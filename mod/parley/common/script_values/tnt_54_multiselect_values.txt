# WHAT ITEM 2.2 IS
# ---------------------------------------------------------------------
# Build 1 stored exactly ONE object per picker in a character variable
# (tnt_title_p, tnt_claim_r, tnt_artifact_p ...). The user asked for
# several at once. 30-V2-DESIGN §1 row 2.2 replaces those six variables
# with six VARIABLE LISTS:
#     tnt_sel_title_p     tnt_sel_title_r
#     tnt_sel_claim_p     tnt_sel_claim_r
#     tnt_sel_artifact_p  tnt_sel_artifact_r
# and the picker panel shows TWO datamodels — "available" (the shipped
# tnt_list_* lists) and "chosen" (tnt_sel_*). A row click MOVES the object
# from one list to the other. That is the whole reason for the two-list
# shape: the engine has NO list-membership datafunction, so a GUI can
# never ask "is this row already chosen". If the object is only ever in
# one list at a time, the question never has to be asked.
#
# THE FOUR THINGS THIS FILE COMPUTES
#   1. six COUNTS         (how many objects are in each selection list)
#   2. six CAP FLAGS      (all hard zeros now — the cap is gone; §2 is the tombstone)
#   3. six VALUATIONS     (what the whole selection is worth, in points)
#   4. the DOMAIN COUNTER (U1(a): what both domains become, and whether
#                          either side ends up over its domain limit)
#
# ---------------------------------------------------------------------
# THE CENTRAL PROOF — every_in_list OVER A VARIABLE LIST, INSIDE A
# common/script_values ENTRY, IS REAL
# ---------------------------------------------------------------------
# GAME\common\script_values\00_diarchy_values.txt:3746-3756, verbatim:
#     pv_overthrow_tally_value = {
#         value = 0
#         every_in_list = {
#             variable = coup_pv_supporters_list
#             limit = { is_powerful_vassal_of = root.liege  is_alive = yes }
#             add = 1
#         }
#     }
# i.e. `variable = <name>` (a VARIABLE list — `list = <name>` is for the
# temporary lists built by add_to_list), a `limit`, and `add` at the top
# level of a named value. That is counter shape 1 exactly.
# Four further sites: 01_dlc_fp1_script_values.txt:268,
# 06_ce1_epidemics_values.txt:2001, 07_ep3_values.txt:4042, :5629.
#
# AND THE PER-ELEMENT-MATHS PROOF, which is the shape used for valuation:
# GAME\common\script_values\00_stress_values.txt:107-150 —
# vanilla's OWN multi-title price, `generous_title_grant_value`:
#     every_in_list = {
#         list = target_titles
#         add = {
#             value = 0
#             if      = { limit = { this.tier = tier_county } add = minor_stress_loss }
#             else_if = { limit = { this.tier = tier_duchy  } add = { value = medium_stress_loss  multiply = 1.25 } }
#             ...
#             multiply = { value = this.tier  add = 1  divide = scope:actor.primary_title.tier }
#         }
#     }
# A full nested `add = { value = 0  if/else_if …  multiply … }` inside an
# in-list iterator inside a script value. Vanilla prices a bag of titles
# with the same machinery this file uses, tier by tier.
# `save_temporary_scope_as` inside such an iterator: 00_basic_values.txt:1858-1868.
# `if = { limit = { … }  every_in_list = { … add = <n> } }` (an iterator
# nested inside an if): GAME\common\script_values\00_interaction_values.txt:350-367
# (`grant_title_opinion_sum_baronies`).
#
# ---------------------------------------------------------------------
# LAW R9 — every value here reads ONLY root (the player) and var: values
# ---------------------------------------------------------------------
# GetScriptValueBreakdown supplies root ONLY (00-ARCHITECTURE §2.7), and
# these values feed the balance through tnt_gain_total_value /
# tnt_loss_total_value, so no value below reads scope:actor,
# scope:recipient or any GUI-supplied scope. The partner is reached the
# way the other 55 values reach him — contract R0.4's prologue
#     var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
# and then `scope:tnt_p ?= { … }` at every read. The `?=` is not
# decoration: the window can be open when the partner dies, and a frame
# can be drawn before the GUI notices (tnt_51_relation_values.txt:51-62).
# Top-level `scope:tnt_p ?= { add = <field> }` is shipped in this mod at
# tnt_51_relation_values.txt:88.
#
# ---------------------------------------------------------------------
# THE PER-ITEM CAP IS 3, AND HERE IS WHY
# ---------------------------------------------------------------------
# 30-V2-DESIGN offers a cap of 3 as the fallback "if performance or
# balance demands it" (§1 row 2.2) and names it again as the mitigation
# for risk R-15 ("Multi-select scale: 5 counties on one side ... error.log
# during apply (five create_title_and_vassal_change cycles in one
# effect)"). THE CAP IS TAKEN, not deferred, for four reasons:
#   1. R-15 is unresolved. Nobody has yet run a five-title hand-over, and
#      the title leg is the one effect in this mod that can corrupt a save
#      (00-ARCHITECTURE §6 item 11). A cap is the cheapest possible
#      insurance and can be raised later by editing four lines.
#   2. Vertical budget. The centre deal sheet has ~786 px for up to 16
#      static rows per side (30-V2-DESIGN §4.2); 6 lists x 3 objects adds
#      at most 18 rows plus 6 group heads, which fits. At 5 per list it
#      does not.
#   3. Balance. Three duchies at 260 base is already 780 points, i.e.
#      more than half of the vassalage term's 1400 ceiling. Beyond that
#      the scales stop being informative.
#   4. The AI. 30-V2-DESIGN §6.4 constraint 3 forbids a convergence loop,
#      so the AI composer picks a package in one pass; a bounded item is
#      one it can actually price.
# THE CAP LIVES IN EXACTLY FOUR PLACES. Change all four together:
#   (a) the six tnt_cap_hit_*_value entries below      (the GUI warning)
#   (b) tnt_multi_add_effect's variable_list_size guard (tnt_35_multiselect.txt)
#   (c) the six tnt_sel_count_* loc strings          (they print "of 3")
#   (d) this comment.
#
# *** v3 ITEM 5 — THE CAP IS OFF FOR THE TWO TITLE LISTS. *** The user overruled
# reasons 1-4 above for titles specifically: "let us remove the limit, and instead
# make exceeding the domain limit give fewer points." So for tnt_sel_title_p and
# tnt_sel_title_r the wall is gone. THE PRICE THAT REPLACED IT IS GONE TOO (user
# item 13; §4b at the foot of this file is now a tombstone): going over the domain
# limit costs nothing at all, and the red domain counter of §4 is the only thing
# left that says so. Concretely: (a) tnt_cap_hit_title_p/_r_value are hard zeros,
# (b) the two title *_add setters no longer route through tnt_multi_add_effect, (c) NO LOC
# CHANGE IS NEEDED — place (c) above is stale: the six shipped tnt_sel_count_*
# strings print "Chosen: N" and never mention 3 (tnt_l_english.yml:436-441), so
# they are already correct for an uncapped list.
#
# *** V4 + THE ARTIFACT/DOMAIN BUG — THE CAP IS OFF FOR ALL SIX LISTS NOW. ***
# V4 removed the ENFORCEMENT for every term alike (tnt_35_multiselect.txt:124-137:
# claims and artifacts delegate to tnt_multi_add_effect, whose variable_list_size
# guard is deleted), but the four claim/artifact cap FLAGS in §2 below kept firing
# at >= 3 selected — reporting a wall that no longer stood. The warning line they
# light prints tnt_err_too_many, whose wording is a DOMAIN-LIMIT sentence left
# over from the v3-item-5 rewording — which is exactly the reported bug "a third
# artifact says I am over my domain limit". The four flags are now hard zeros like
# the title pair (see §2 for the full account). Of the four places above: (a) all
# six flags are hard zeros, (b) gone from tnt_35 for every term, (c) stale as
# noted, (d) is this comment. Reason 1 (risk R-15, several
# create_title_and_vassal_change cycles in one effect) is NOT resolved by this
# change and is now a live risk on the title leg — it is reported upward rather
# than silently accepted.
#
# ---------------------------------------------------------------------
# NOTHING HERE IS A desc-BEARING VALUE
# ---------------------------------------------------------------------
# Contract §4 rule 3: exactly two values in this mod carry `desc`
# (tnt_balance_value and tnt_ai_accept_value). The six valuations below
# are plain numbers, and the integrator wires them into tnt_balance_value
# with the desc keys that ALREADY exist for the single-object rows —
# tnt_bd_title_p/_r, tnt_bd_claim_p/_r, tnt_bd_artifact_p/_r. So item 2.2
# needs ZERO new breakdown loc keys, and R10 (no VALUE token in a
# breakdown desc) is satisfied by keys that already satisfy it.

# 3. THE SIX VALUATIONS
#
# Each one is the multi-object twin of a shipped single-object value, and
# every number, every multiplier and every trigger is copied from it so
# that a one-title deal prices EXACTLY as it did in build 1:
#   tnt_val_title_multi_p_value    <- tnt_val_title_p_value    (tnt_50_values.txt:1550)
#   tnt_val_title_multi_r_value    <- tnt_val_title_r_value    (:1587)
#   tnt_val_claim_multi_p_value    <- tnt_val_claim_p_value    (:1689)
#   tnt_val_claim_multi_r_value    <- tnt_val_claim_r_value    (:1693)
#   tnt_val_artifact_multi_p_value <- tnt_val_artifact_p_value (:1949)
#   tnt_val_artifact_multi_r_value <- tnt_val_artifact_r_value (:2021)
# The tier bases 15 / 30 / 45 / 60 / 75 are inlined rather than read
# from tnt_tier_base_title_p_value, because those four shipped values
# dereference the single object variables (`var:tnt_title_p ?= { … }`)
# and there is no per-element equivalent to hand a value name.
# tier constants: GAME\common\script_values\00_title_tiers_values.txt:1-7.
#
# ===========================================================================
# v3 ITERATION 2 — THE LADDER AND THE CLAIM FACTOR BOTH MOVED. KEEP THEM IN
# STEP WITH tnt_50_values.txt §4.B OR A ONE-TITLE DEAL WILL PRICE TWICE OVER.
# ===========================================================================
#   tier ladder   45 / 110 / 260 / 620 / 1250   ->   15 / 30 / 45 / 60 / 75
#   claim factor  x0.35                          ->   x0.5
#   artifact      40 / 90 / 180 / 350            ->   35 / 75 / 100 / 150
# The derivations are written out once, in tnt_50_values.txt §4.B (the ladder is
# vanilla's grant-title opinion ladder 20/40/60/80/100 from
# GAME\common\script_values\00_interaction_values.txt:359,378,397,416,435, times the
# 0.75 at which opinion enters an acceptance sum,
# GAME\common\scripted_modifiers\00_marriage_scripted_modifiers.txt:662-670) and in
# tnt_50_values.txt §4.C items 7 and 10. THE SIX VALUES BELOW MUST AGREE WITH THEIR
# SINGLE-OBJECT TWINS TO THE POINT, because the header promise of this section is
# that "a one-title deal prices EXACTLY as it did in build 1" — that promise is now
# "prices EXACTLY as its single-object twin does", and it is the only thing keeping
# the deal sheet and the breakdown from disagreeing.
#
# WHICH MULTIPLIERS ARE PER ELEMENT AND WHICH ARE PER DEAL — this is the
# one judgement call in this section, and it follows the semantics of each
# test rather than convenience:
#   PER ELEMENT (inside the nested add, evaluated in the TITLE's scope)
#     x1.4  the land is the receiver's de jure  (a property of that title)
#     x1.25 the land is culturally the receiver's (a property of that title)
#     rarity buckets for artifacts               (a property of that artifact)
#   PER DEAL (top level, evaluated in the PLAYER's scope)
#     x1.2  the two realms border each other     (a property of the pair)
#     x1.3  the current holder is the weaker side (a property of the pair)
#     x0.5  a claim is a licence, not land        (a property of the term)
# A top-level `multiply` after an iterator applies to the accumulated
# total — vanilla's own shape, GAME\common\script_values\00_stress_values.txt:143-147.
#
# `NOT = { … }` and the tier tests run inside every_in_list, where the
# iterated element IS the current scope, so `tier = tier_county` and
# `title_province ?= { … }` need no dereference at all. The character-side
# neighbour trigger is therefore re-scoped with `root = { … }`.
###############################################################################

# --- 6. CEDE TITLES, player's side ------------------------------------------
# The de jure walk is any_this_title_or_de_jure_above, NOT the bidirectional
# any_in_de_jure_hierarchy — that substitution mis-priced every ceded duchy in
# an earlier revision of tnt_50_values.txt and its warning is repeated at
# tnt_50_values.txt:1534-1544. Verbatim vanilla shape:
#   GAME\common\casus_belli_types\07_ep3_wars.txt:3780
#     any_this_title_or_de_jure_above = { holder ?= scope:attacker.liege }
tnt_val_title_multi_p_value = {
	# NO ROOT IN AN INTERACTION'S on_accept, so the value names the scope it stands on.
	# Full argument at tnt_52_marriage_values.txt:823-839. Guarded, because a parent
	# value or effect may already hold tnt_me and re-saving it is an error in itself.
	if = {
		limit = { NOT = { exists = scope:tnt_me } }
		if = {
			limit = { exists = scope:actor }
			scope:actor = { save_temporary_scope_as = tnt_me }
		}
		else = { save_temporary_scope_as = tnt_me }
	}
	value = 0
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = {
			exists = var:tnt_partner
			has_variable_list = tnt_sel_title_p
		}
		every_in_list = {
			variable = tnt_sel_title_p
			add = {
				value = 0

				if = {
					limit = { tnt_scaled_valuation_enabled_value > 0 }
					add = tnt_scaled_county_land_value
				}
				else_if = {
					limit = { tier = tier_barony }
					add = 15
				}
				else_if = {
					limit = { tier = tier_county }
					add = 30
				}
				else_if = {
					limit = { tier = tier_duchy }
					add = 45
				}
				else_if = {
					limit = { tier = tier_kingdom }
					add = 60
				}
				else_if = {
					limit = { tier = tier_empire }
					add = 75
				}

				# The land is already his by right.
				if = {
					limit = {
						any_this_title_or_de_jure_above = { holder ?= scope:tnt_p }
					}
					multiply = 1.4
				}
				# The people down there are his people. `?=` because only county
				# tier has a province (tnt_50_values.txt:1546-1549).
				if = {
					limit = {
						title_province ?= { culture ?= scope:tnt_p.culture }
					}
					multiply = 1.25
				}
			}
		}
		# Per deal, not per title: adjacency is a property of the two realms.
		if = {
			limit = {
				scope:tnt_me = { character_is_land_realm_neighbor = scope:tnt_p }
			}
			multiply = 1.2
		}
	}
}
