# THE FIVE RULES THAT SHAPE EVERY VALUE BELOW
# ---------------------------------------------------------------------------
# 1. root is ALWAYS the player. `GuiScope.SetRoot( GetPlayer.MakeScope )
#    .GetScriptValueBreakdown( … )` supplies root and nothing else — an extra
#    GUI scope would silently break the tooltip. So these values read only
#    root and var: values. (Law 6 / contract §4 rule 1.)
# 2. The partner is reached through the R0.4 prologue and never as a GUI scope:
#        var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
#    PROOF that `var:<obj> ?= { … }` works inside a script value:
#      GAME\common\script_values\10_ach_values.txt:1414-1428
#        oath_purge_pretenders_claimants = {
#            value = 0
#            var:purge_pretenders_target_title ?= { every_claimant = { … add = 1 } }
#        }
#    PROOF that `save_temporary_scope_as` works inside a script value:
#      GAME\common\script_values\00_scheme_values.txt:2434-2437
#        base_odds_prediction_target_is_char_value = {
#            scope:target ?= { save_temporary_scope_as = temp_target }
#            add = base_odds_prediction_guts_value
#        }
#      — note that vanilla also relies on the temp scope surviving into a
#        *different* script value, which is exactly what we do here.
# 3. Never compare two variables (Law 4 / R0.3). Cross-character differences are
#    folded into tnt_prestige_edge_value / tnt_tier_edge_value / the two
#    power-ratio values and only those are compared against literals.
#    `var:x > <literal>` is legal and is what we use for the selection tests:
#      GAME\common\script_values\00_activity_values.txt:541  `var:protected_alcohol_stores > 0`
# 4. Only tnt_balance_value and tnt_ai_accept_value carry `desc =`. Every other
#    value in this mod is a plain number (contract §4 rule 3 / acceptance 15).
#    desc keys must NOT contain $VALUE$ — the widget renders the number in its
#    own right-aligned column (Law 8, GAME\gui\shared\value_breakdown.gui:1935-1955).
# 5. Every division is guarded (`divide = { value = X min = 1 }`) and every
#    object-valued variable read is guarded by `exists =` or `?=` (Law 12).
#

# ===========================================================================
# CALIBRATION — v3 ITERATION 2: THE SCALE IS NOW VANILLA'S OWN
# ===========================================================================
# THE COMPLAINT THIS ANSWERS, in the user's words: "if I arrange a marriage
# through the game it says +12 points, but the same marriage inside our deal is
# counted with negative points. And this must apply to every option."
#
# WHAT THE OLD SCALE WAS AND WHY IT HAD TO GO.
# Iterations 0-1 priced everything as "100 points ~= one year of the PARTNER'S
# income". That currency is internally consistent but it is NOT vanilla's, and it
# is not even a fixed multiple of vanilla's — it drifts with the partner's income.
# A duke on 150 gold a year saw our 100 points for 150 gold where vanilla pays
# +10; a rich emperor on 600 a year saw our 100 points for 600 gold where vanilla
# still pays about +40. So no single rescaling could ever line the two up, and
# every term in the window read roughly ten times its vanilla worth while the
# threshold subtraction pushed the total the other way.
#
# THE SCALE NOW: **A RAW ACCEPTANCE POINT, EXACTLY AS VANILLA COUNTS IT.**
# `ai_accept` in vanilla is a raw point sum whose stated default base is 0 —
# GAME\common\character_interactions\00_prison_interactions.txt:758
#   `base = 0 # Try to make it 0 for most interactions`
# (same comment 03_fp2_interactions.txt:2240) — and `> 0` means accept. The bands
# vanilla actually uses, measured across its own interactions:
#     hard block   -975 .. -1000     clear no      -50 .. -200
#     marginal yes     0 .. +15      comfortable   +25 .. +75
#     forced yes    +100 .. +1000
# Every invented number below is snapped to vanilla's own offset ladder
#     very_low 10 / low 20 / medium 35 / high 50 / very_high 75 / dominant 200
# GAME\common\script_values\00_ai_values.txt:22-34.
# (NOTE for anyone re-checking: the ladder is at :22-34. An earlier revision of
# this header cited :70-82, which is wrong; :60-64 is the unrelated
# *_ai_values_divergence 150/200/250/300/350 personality-distance scale.)
#
# HOW A RESOURCE BECOMES A POINT — THE BRIBE-MENU ROSETTA STONE.
# The one place vanilla states the exchange rate is the invite-agent bribe menu:
# each scope hands over a named amount (GAME\common\script_values\00_scheme_values.txt)
# and buys a fixed number of acceptance points
# (GAME\common\scripted_modifiers\00_scheme_scripted_modifiers.txt):
#     bribe_value gold          -> +10   SSM:552-566   SV:51-90   (50, x2 below duke, x3 duke+)
#     prestige_bribe_value      -> +20   SSM:647-666   SV:151-164 (150 + 25*actor tier + 25*recipient tier)
#     piety_bribe_value         -> +20   SSM:740-754   SV:196-209 (100 + 25 + 25)
#     influence_bribe_value     -> +20   SSM:668-687   SV:181-194 (100 + 25 + 25)
# Divide one by the other and you get the four unit prices, which are what
# tnt_gold_per_point_value (§4.A here) and tnt_prestige/piety/influence_per_point_value
# (tnt_53_currency_values.txt §0b) return:
#     gold      10 below duke, 15 duke and up      (flat: the tier multiplier saturates)
#     prestige  7.5  + 1.25 * (my tier + his tier) ->  12.5 / 15 / 17.5 / 20
#     piety     5    + 1.25 * (my tier + his tier) ->  10 / 12.5 / 15 / 17.5
#     influence 5    + 1.25 * (my tier + his tier) ->  10 / 12.5 / 15 / 17.5
# THE INCOME NORMALISATION IS GONE, AND THAT IS DELIBERATE: vanilla's rates key
# off TIER, never off income (SV:63-75, :151-209 above). A flat tier-driven rate
# is what vanilla actually uses, so it is what we use; keeping the old divisor
# would have re-introduced exactly the drift described three paragraphs up.
#
# WHERE THE THRESHOLD WENT — see the long note above tnt_threshold_value. Short
# version: it is no longer a 15..95 constant offset folded into the headline; it
# is vanilla's `base`, zero for an ordinary partner, and it is still one of the
# rows that sum to the headline, so `> 0` still means accept.
#
# Everything is still priced in the PARTNER'S eyes, in both columns: the _p values
# are what he gains, the _r values are what he gives up. Both are >= 0; the sign
# is applied once, by tnt_balance_value.
#
# PER-TERM ANCHORS (the file:line beside each number below is the proof; this is
# the index):
#   gold / prestige / piety / influence  the four unit prices above
#   alliance            40 x power ratio, x the ally-glut ladders on BOTH sides,
#                       + the imported bias block, clamped 0..150 (v4 item 22).
#                       Vanilla's DESIRES_ALLIANCE is +40 neutral / +100 friend,
#                       MSM:140,256; the glut is MSM:181-204 and
#                       00_alliance.txt:2126-2169; the bias is negotiate_alliance's
#                       own ai_accept rows. Full argument at §3.
#   non-aggression      ~10 — vanilla prices the pact itself at 0
#                       (purchase_truce ai_accept base = 0, 03_fp2_interactions.txt:2241)
#   marriage            base 0 and vanilla's own MSM rows, tnt_52_marriage_values.txt
#   cede title          15/30/45/60/75 = the grant-title opinion ladder
#                       20/40/60/80/100 (00_interaction_values.txt:359,378,397,416,435)
#                       x 0.75, the rate at which opinion enters acceptance (MSM:667)

# --- HOW MANY GOLD BUY ONE ACCEPTANCE POINT (v3 iteration 2) ------------------
# THE SINGLE MOST IMPORTANT NUMBER IN THE MOD. It is the divisor for the gold term,
# and tnt_53_currency_values.txt derives its three
# sibling rates the same way, so all four currencies stay mutually consistent.
#
# DERIVATION, from vanilla and nothing else. The invite-agent bribe menu hands over
# `bribe_value` gold and buys +10 acceptance:
#   GAME\common\scripted_modifiers\00_scheme_scripted_modifiers.txt:552-566
#     modifier = { add = { value = 10 … } scope:gift ?= yes … }
#   GAME\common\script_values\00_scheme_values.txt:51-90
#     bribe_value = { value = 50 … recipient tier < tier_duchy -> multiply = 2
#                                  recipient tier >= tier_duchy -> multiply = 3 }
# So   below duke  50 x 2 = 100 gold / 10 pts = 10 gold per point
#      duke and up 50 x 3 = 150 gold / 10 pts = 15 gold per point
# and it stops there — the tier multiplier saturates at duke, which is why gold is
# the one FLAT rate of the four (the other three keep climbing +2.5 per tier step).
# The parity table records this as the correction to the old "150 gold = +10"
# claim: that figure is true at duke tier and above only.
#
# WHOSE TIER: THE RECIPIENT'S, i.e. the partner's — vanilla reads
# `scope:recipient.primary_title.tier` (SV:63-75) and the partner is the one being
# bought in every row of this file. `highest_held_title_tier` rather than
# `primary_title.tier` because it needs no `?=` guard for a landless character and
# the mod already uses it in tnt_tier_edge_value.
# `highest_held_title_tier >= tier_duchy` INSIDE A SCRIPT VALUE'S OWN `limit`, which
# is exactly our context: REAL,
#   GAME\common\script_values\00_activity_values.txt:1356
#     `limit = { highest_held_title_tier >= tier_county }`
#   GAME\common\script_values\00_artifact_values.txt:180-198
#     the full county / duchy / kingdom / empire ladder, one `>=` per rung
# (also GAME\common\council_tasks\00_chancellor_tasks.txt:876 and
#  GAME\common\achievements\standard_achievements.txt:448 outside script values).
#
# `bribe_value` also carries `+ ai_greed / 4`, which is deliberately NOT copied
# here: ai_greed already moves tnt_threshold_value, and charging it twice would put
# the partner's greed into the price of gold AND into his asking price.
#
# --- THE BASE RATE, EXTRACTED (V19) ------------------------------------------
# One literal, two readers: the opening row of tnt_gold_per_point_value below,
# and A13's affordability gate tnt_ai_art_afford_gap_value (end of
# common\script_values\tnt_56_ai_values.txt), which deliberately reads the BASE
# rate and not the live duke+ rate - V18's recorded charter, "refuses only the
# letters that could not have closed under ANY currency". V18 hardcoded that
# gate as four gold literals (points x 10) and the ladder then moved out from
# under them; a stale-literal gate is impossible while both sites read this
# one name.
tnt_gold_base_rate_value = {
	value = 10
}

tnt_gold_per_point_value = {
	value = tnt_gold_base_rate_value
	var:tnt_partner ?= {
		if = {
			limit = { highest_held_title_tier >= tier_duchy }
			add = 5
		}
	}
	min = 1
}

# --- signed edges: > 0 means the PLAYER is ahead (R0.3) ----------------------

# --- affordability: > 0 means the giver cannot pay ---------------------------
# Read by tnt_send_offer's is_valid as `<= 0` (contract §5 group G).
# gold: field, GAME\common\script_values\00_basic_values.txt:459
#
# DEFECT FOUND AND FIXED IN v2 (not in the six of §9 — found by reading, and it
# is the reason the three new currency shortfalls in tnt_53_currency_values.txt
# are shaped the way they are).
# The v1 bodies were:
#     value = 0
#     if = { limit = { exists = var:tnt_gold_p }  add = var:tnt_gold_p }
#     subtract = gold
# The `subtract = gold` sat OUTSIDE the if, so a ruler IN DEBT scored a positive
# shortfall with nothing offered at all: gold = -50, nothing on the table
#   =>  0 - (-50) = +50 > 0  =>  tnt_send_offer.is_valid refuses EVERY deal,
# including a deal with no gold in it, with the tooltip "You cannot afford the
# gold you are offering" while the gold row reads 0. Gold really can go negative
# in CK3 — vanilla tests `gold < 0` (GAME\common\character_interactions\00_gift.txt:537,
# :640, :759) and `is_in_debt = no` (00_war.txt:58).

# --- 1. GOLD, one-time ------------------------------------------------------
# v3 ITERATION 2 — VANILLA RATE, AND THE OLD INCOME DIVISOR IS GONE.
# amount / tnt_gold_per_point_value, i.e. one point per 15 gold at duke tier and
# above, per 10 gold below it. The derivation and the two vanilla call sites are in
# tnt_gold_per_point_value's own header (§4.A).
# ANCHOR CHECK: 300 gold to a duke reads 300/15 = +20, which is exactly what
# vanilla's `gift_significant` band pays for `greater_bribe_value` = 2 x 150 gold
# (GAME\common\scripted_modifiers\00_scheme_scripted_modifiers.txt:568-582,
#  `value = 20`). 150 gold to the same duke reads +10, SSM:552-566. Exact parity.
#
# NO CAP AND NO PERSONALITY RIDER, both on purpose.
#   * Vanilla's two gold bands are 1x -> +10 and 2x -> +20, i.e. LINEAR, so a
#     linear uncapped rate is the faithful extrapolation. A player who wants to
#     put 5000 gold on the table gets proportional credit, as he should.
#   * Vanilla's `greedy` rider is a FLAT +10 per band (+100 % on the first band,
#     +50 % on the second), which does not translate into any single proportional
#     factor; and ai_greed already moves tnt_threshold_value. Charging greed twice
#     would price the same trait on both sides of the same trade.
# `gift_interaction` is NOT usable as an anchor here: its `add = 100 desc = GOLD_REASON`
# (GAME\common\character_interactions\00_gift.txt:440-445) is flat regardless of
# the amount sent.
tnt_val_gold_p_value = {
	value = 0
	if = {

			exists = var:tnt_gold_p
			var:tnt_gold_p > 0
		}
		add = {
			value = var:tnt_gold_p
			divide = { value = tnt_gold_per_point_value  min = 1 }
		}
	}
}

#   GAME\common\scripted_modifiers\00_marriage_scripted_modifiers.txt:255-256 (`value = 100`)

# could read negative for a partner stronger than the player, and vanilla never
# prices a bare alliance below zero (its only negative alliance row is the -100
# enemy stance, MSM:324, which our faith / opinion / relation rows already carry).

# =============================================================================
# V4 ITEM 22 — THE ALLY GLUT, AND THE EXPLOIT IT CLOSES
# =============================================================================
# THE EXPLOIT the user named: an alliance costs the player nothing to hand over and
# was priced at a flat 40 x ratio however many alliances he had already sold. Open
# the table with every neighbour in turn and the same promise buys a county from each
# of them. Nothing in the ledger noticed the tenth alliance was worth less than the
# first — nothing in the ledger noticed the player HAD ten.
#
# THE OLD PARTIAL FIX, AND WHY IT WAS WORSE THAN NOTHING: a flat x0.5 when the
# PARTNER held 2+ allies (here) plus a -15-per-partner-ally row in
# tnt_relmod_ally_value gated on `var:tnt_alliance_p > 0` (tnt_51_relation_values.txt
# §8). Both charged the wrong man — the partner, never the serial allier — and the
# gated relmod row broke I4 outright: ticking the alliance box switched on a penalty
# worth up to -45 x unit, so ADDING a term to the table could LOWER the headline.
# That row is deleted in this pass and the entire ally question now lives here as a
# MULTIPLIER, which is the one shape that cannot break I4: a multiplier in [0,1] can
# only pull a non-negative addend toward zero, never through it.
#
# THE NUMBERS ARE VANILLA'S, IN VANILLA'S OWN SHAPE. MSM:181-204 does not subtract
# per ally, it MULTIPLIES:
#     scope:actor = { any_ally = { NOR = { target_is_liege_or_above = scope:actor
#                                          target_is_vassal_or_below = scope:actor }
#                                  count >= 2 } }
#       -> scope:actor = { every_ally = { limit = { <the same NOR> } multiply = 0.5 } }
# i.e. x0.5 per non-vassal, non-liege ally once he has two of them:
#     0-1 ally -> x1      2 -> x0.25      3 -> x0.125      4 -> x0.0625
# THAT ROW COUNTS THE ACTOR'S ALLIES — the man asking. The comment that used to stand
# here cited it (as "MSM:193-204") for a rider on the RECIPIENT's ally count, which is
# not what it says; that mis-attribution is corrected in this pass, in this file and
# in its AI twin. The recipient's own ally count IS charged by vanilla, but by a
# different row: the -15 each of 00_alliance.txt:2148-2169
# (`THEIR_EXISTING_ALLIANCES_REASON`), whose actor-side twin is :2126-2146. Vanilla
# therefore charges BOTH sides, and so do we:
#     tnt_ally_glut_self_value      the PLAYER's allies    MSM:181-204 + 00_alliance.txt:2126-2146
#     tnt_ally_glut_partner_value   the PARTNER's allies   00_alliance.txt:2148-2169
# Both are rendered multiplicatively, in vanilla's marriage-modifier shape rather than
# the alliance interaction's -15 shape, because a multiplier is the only I4-safe form
# and because vanilla's own alliance-DESIRE row is already multiplicative.
#
# WHY THE MIN MOVED 10 -> 0: with a floor of 10 the glut was invisible. 40 x ratio 1
# x 0.0625 = 2.5 would have been clamped back up to 10, i.e. a man with four allies
# would still have been paid a quarter of the even-strength price for a promise worth
# nothing. A floor of 0 also keeps I6 (the price is still >= 0 in its own value) and
# I3 (a term that can only reach 0 can never invert a generous deal).
#
# every_ally = { limit = {…} multiply = 0.5 } is NOT used: contract v1 R11 forbids it
# this pass because that form is unproven inside common/script_values in this mod. The
# `any_ally = { … count >= N }` ladder below reproduces it exactly at every rung that
# can be reached. The 0.0625 floor is REASONED, not imported: it is the fourth rung
# written out as a clamp, so that a man with nine allies prices his ninth alliance at
# the same 6.25% as his fourth instead of at 0.2% — which would round to nothing and
# read as a broken term rather than as a cheap one.
# target_is_liege_or_above / target_is_vassal_or_below inside a script value:
#   GAME\common\script_values\00_lifestyle_values.txt:831
#   GAME\common\script_values\07_ep3_values.txt:622
# The NOR is vanilla's and it carries real meaning: your own vassals and your own
# liege are not "friends you already have", they are your realm.
tnt_ally_glut_self_value = {
	# NO ROOT IN AN INTERACTION'S on_accept, so the value names the scope it stands on.

	# value or effect may already hold tnt_me and re-saving it is an error in itself.
	if = {
		limit = { NOT = { exists = scope:tnt_me } }
		if = {
			limit = { exists = scope:actor }
			scope:actor = { save_temporary_scope_as = tnt_me }
		}
		else = { save_temporary_scope_as = tnt_me }
	}
	value = 1
	if = {
		limit = {
			scope:tnt_me ?= {
				any_ally = {
					NOR = {
						target_is_liege_or_above = scope:tnt_me
						target_is_vassal_or_below = scope:tnt_me
					}
					count >= 2
				}
			}
		}
		multiply = 0.25
	}
	if = {
		limit = {
			scope:tnt_me ?= {
				any_ally = {
					NOR = {
						target_is_liege_or_above = scope:tnt_me
						target_is_vassal_or_below = scope:tnt_me
					}
					count >= 3
				}
			}
		}
		multiply = 0.5
	}
	if = {
		limit = {
			scope:tnt_me ?= {
				any_ally = {
					NOR = {
						target_is_liege_or_above = scope:tnt_me
						target_is_vassal_or_below = scope:tnt_me
					}
					count >= 4
				}
			}
		}
		multiply = 0.5
	}
	min = 0.0625
}

# --- 6. CEDE TITLE ----------------------------------------------------------
# Tier base, then three multipliers: x1.4 the land is his de jure, x1.25 the
# land is culturally his, x1.2 it borders him.
#
# The de jure test is contract §4.C's `any_this_title_or_de_jure_above`, which
# walks the offered title and its de jure LIEGES UPWARD only. The exact shape
# used below — `any_this_title_or_de_jure_above = { holder ?= <character> }` — is
# verbatim vanilla at
#   GAME\common\casus_belli_types\07_ep3_wars.txt:3780
#     (`any_this_title_or_de_jure_above = { holder ?= scope:attacker.liege }`)
# and in the fuller form at GAME\common\casus_belli_types\00_dejure_war.txt:39-48.
#
# DO NOT substitute `any_in_de_jure_hierarchy` here: that iterator is
# BIDIRECTIONAL and walks the de jure tree DOWNWARD as well, so without a `tier`
# filter and a `continue` block it also matches every barony and county beneath
# the offered title. Vanilla always constrains it — see
# GAME\common\script_values\00_war_values.txt:477-486
# (`tier > tier_county` + `any_in_de_jure_hierarchy = { tier = tier_county … }`)
# and GAME\common\casus_belli_types\00_conquest.txt:490-493 (`continue = { … }`).
# An earlier revision of this file used it behind a `# FALLBACK:` note claiming
# `any_this_title_or_de_jure_above` had zero hits in the install. That claim was
# false — the identifier occurs 85+ times under GAME\ — and the substitute
# mis-priced every ceded duchy and kingdom.
#
# title_province ?= { culture … }: `title_province.culture` is proven at
# GAME\common\factions\00_factions.txt:1344-1354 and
# GAME\common\factions\00_populist_faction.txt:293. `?=` because only county
# tier has a province; a duchy or kingdom would otherwise error.
tnt_val_title_p_value = {
	value = 0
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = {
			exists = var:tnt_title_p
			exists = var:tnt_partner
		}
		add = {
			value = tnt_tier_base_title_p_value
			if = {
				limit = {
					var:tnt_title_p ?= {
						any_this_title_or_de_jure_above = { holder ?= scope:tnt_p }
					}
				}
				multiply = 1.4
			}
			if = {
				limit = {
					var:tnt_title_p ?= {
						title_province ?= { culture ?= scope:tnt_p.culture }
					}
				}
				multiply = 1.25
			}
			if = {
				limit = { character_is_land_realm_neighbor = scope:tnt_p }
				multiply = 1.2
			}
		}
	}
}

###############################################################################
# THE OFFER, FLOORED AT ZERO — the base the opinion multiplier scales (V4)
#
# WHY IT EXISTS, and it is a real defect this closes rather than tidiness.
# tnt_gain_total_value CAN STILL BE NEGATIVE, and THE FLOOR MUST STAY. One family
# of its members is signed:
#   the nine tnt_val_ob_*_value  pre-signed from the subject's point of view, so
#                                an exemption the PLAYER extracts arrives negative
# (tnt_domain_penalty_p_value used to be the second such member; it was removed with
# the domain-limit discount, user item 13. The nine obligation rows on their own are
# enough to drive the total below zero, so nothing here may be relaxed.)
# So a treaty where the player mostly EXTRACTS things can carry a negative "gift
# total". Fix 5 multiplied that total by (opinion / 100), and with a negative total
# and a negative opinion the product is POSITIVE: hatred would have improved the
# deal. That is the sign error the user asked to be ruled out on both sides of zero.
#
# THE FLOOR IS THE FIX, and it is also the honest reading: the multiplier answers
# "how much is what you are GIVING worth to him". If you are giving nothing, there
# is nothing for affection to inflate or for loathing to devalue, so the answer is
# zero - not a bonus for being hated. What the player TAKES keeps its full weight
# either way, in tnt_loss_total_value, which no multiplier touches.
#
# THE FOUR CASES, all now correct:
#   gifts > 0, opinion > 0   ->  positive row, up to +100% of the offer
#   gifts > 0, opinion < 0   ->  negative row, down to cancelling the offer entirely
#   gifts <= 0, opinion > 0  ->  0. Nothing given, nothing to reward.
#   gifts <= 0, opinion < 0  ->  0. Nothing given, so nothing to devalue - and, in
#                                particular, no accidental bonus.
#
# It is a separate named value and not `multiply = { value = … min = 0 }` inline
# because a BLOCK as the operand of `multiply` is not a shape this mod has proven
# in vanilla, while `value = <named value>` with a `min` is used all over this file.
###############################################################################
tnt_gain_positive_value = {
	value = tnt_gain_total_value
	min = 0
}

###############################################################################
# ONE PER CENT OF THE OFFER — the unit every modifier is now measured in
#
# ===========================================================================
# THE RULE THIS IMPLEMENTS, and it is absolute: "an empty treaty must ALWAYS read
# zero, and every modifier acts only as a multiplier on the points of the options."
# ===========================================================================
# Before V4 the headline was
#       gain - loss + (eight relationship rows) - threshold
# and every one of those rows was a FLAT number of points. So opening the window on
# a stranger of another faith already read -10 before anything was placed on the
# table, a friend arrived at +35, and a treaty could be carried by facts about the
# two rulers rather than by its own terms. That is the whole complaint, and the
# opinion multiplier of fix 5 only fixed one row of eight.
#
# NOW EVERY MODIFIER IS A PERCENTAGE OF WHAT IS BEING OFFERED. Each row keeps the
# number it always had - faith -10, a friend +35, opinion up to +-100 - but that
# number is now read as PER CENT and multiplied by this unit:
#       row's contribution = <the row's number> x (the offer / 100)
# so the headline becomes
#       gain x (1 + sum of the rows / 100) - loss + threat
# and with nothing on the table the sum is zero times anything, which is zero. The
# window opens at 0 for every partner in the game, without a single special case.
#
# WHY THE OFFER AND NOT THE WHOLE TRADE. The multiplier answers "how much is what
# you are GIVING worth to him", which is a question about his feelings. What he
# would HAND OVER is priced by tnt_loss_total_value and keeps its full weight: a
# friendly ruler is generous with what he receives, not blind to what is taken from
# him. Scaling the net instead would make a generous friend refuse a lopsided treaty
# twice as hard, which is backwards.
#
# THE FLOOR AT ZERO IS INHERITED from tnt_gain_positive_value above and it is what
# keeps the signs honest in all four quadrants - the table at its definition.
#
# THE THREAT IS DELIBERATELY OUTSIDE THIS. Fear is not a modifier on generosity; it
# is its own term, and it must keep working on a ruler whose every other modifier is
# negative. It is zero on an empty treaty anyway, because its variable is unset.
#
# ===========================================================================
# V15 - THE CONSEQUENCE THIS DESIGN HAS TO OWN, AND THE STANDING RULE THAT
# FOLLOWS FROM IT. Written down because the round that found it had to derive it
# from scratch, and the derivation is not obvious from the rule above.
# ===========================================================================
# THE CONSEQUENCE: A TREATY WITH ONE SMALL TERM HAS ALMOST NO MODIFIER STACK, BY
# CONSTRUCTION. Every relationship row contributes `row_number x (offer / 100)`,
# so if the offer is single-digit the unit is about 0.05 and opinion (+-100),
# faith (-35), culture, war, allies and the greed threshold all contribute about
# nothing. That is not a bug in any of those rows - it is the exact price of the
# rule stated above, "an empty treaty must ALWAYS read zero". A multiplier cannot
# be large when there is nothing to multiply, and no clamp or floor can rescue it
# without re-introducing the flat points that made the window open at -10.
#
# HOW IT WAS FOUND, so the symptom is recognisable next time: the user priced the
# same marriage in vanilla and in this mod and got +150 against +5 (and, a round
# earlier, -150 against +1). Neither number came from the relationship layer being
# wrong. The marriage TERM was underpriced, the offer was therefore tiny, and the
# tiny offer then flattened every modifier that would otherwise have separated the
# two cases. One underpriced term reads as "the whole modifier stack is broken".
#
# THE MITIGATION IS AUTOMATIC AND NEEDS NO CODE HERE: fix the term's own price and
# the stack comes back for free, because the unit is a percentage OF that price.
# When tnt_52_marriage_values.txt gained vanilla's DREAD ladder in V15 a cowed
# vassal's pair gain went from about 0 to about 150, the unit went from 0.00 to
# 1.50, and opinion +50 went from contributing about +2 to about +75 - which is
# vanilla's own +-75 opinion row, reproduced by this architecture rather than by a
# new row. Nothing in this file changed.
#
# THE STANDING RULE, AND IT IS THE ONE TO REMEMBER:
#   A VANILLA ROW WORTH MORE THAN ABOUT 50 POINTS THAT DESCRIBES THE TWO RULERS
#   MUST BE PORTED INTO THE TERM'S OWN PRICE, NEVER INTO A relmod ROW - or the
#   percentage above will multiply it to nothing on exactly the small treaties
#   where the player is most likely to be checking our number against vanilla's.
# A relmod row is the right home for a STANDING fact that should scale with how
# much is on the table (does he like you, is he your kin, is he at war). It is the
# wrong home for a large fact about a SPECIFIC term, and "large" here means
# roughly "more than half of what an ordinary term is worth".
# The worked example, with its full argument and its vanilla line numbers, is
# tnt_52_marriage_values.txt value 10, tnt_marriage_dread_value.
###############################################################################
tnt_gain_scale_unit_value = {
	value = tnt_gain_positive_value
	divide = 100
}

###############################################################################
# THE MULTIPLIER ITSELF — tnt_deal_mod_sum_value and tnt_deal_mult_value
#
# The headline scales the offer row by row, which keeps the breakdown tooltip
# honest. But two other places need the multiplier AS ONE NUMBER:
#   * the marriage preview in vanilla's matchmaker, which the user requires to show
#     "the same number of points that will enter the treaty" - and what enters the
#     treaty is the pair's worth AFTER this multiplier;
#   * anything that wants to tell the player "he values your offer at x1.35".
#
# tnt_deal_mod_sum_value is the sum of the seven relationship percentages minus the
# threshold percentage - i.e. the whole modifier stack in per cent. It must be
# evaluated ON THE PLAYER, because every row inside it reads var:tnt_partner off the
# current scope.
#
# tnt_deal_mult_value wraps it and solves the scope problem the 2026-08-13 run
# exposed: inside an interaction the evaluating scope may be scope:actor, or not a
# character at all. So it evaluates the sum inside `scope:actor = { … }` when an
# interaction is what we are in, and on the current scope otherwise. Either way it
# returns 1.0 when nothing stands between the two rulers, and `min = 0` keeps a pile
# of hatred from turning the offer NEGATIVE - at worst your gifts are worth nothing.
###############################################################################
tnt_deal_mod_sum_value = {
	value = 0
	add = tnt_relmod_opinion_value
	add = tnt_relmod_faith_value
	add = tnt_relmod_culture_value
	add = tnt_relmod_kin_value
	add = tnt_relmod_relation_value
	add = tnt_relmod_war_value
	add = tnt_relmod_ally_value
	subtract = tnt_threshold_value
}

tnt_deal_mult_value = {
	value = 100
	if = {
		limit = { exists = scope:actor }
		scope:actor = { add = tnt_deal_mod_sum_value }
	}
	else = {
		add = tnt_deal_mod_sum_value
	}
	divide = 100
	min = 0
}


###############################################################################
# tnt_deal_floor_value — THE min = 0 ABOVE, MADE TO EXIST IN THE HEADLINE TOO
#
# THE BUG THIS FIXES, IN THE USER'S OWN WORDS: "у партнёра мнение о мне -100, я
# предлагаю ему 1000 золота - очки улетают далеко в минус". A pure gift, nothing
# asked in return, priced WORSE the more gold was put on the table.
#
# WHY IT HAPPENED. The multiplicative model has two implementations, and only one
# of them carried the clamp. tnt_deal_mult_value above is the one-number wrapper
# used by every preview and by autobalance, and it ends in `min = 0`. The HEADLINE
# does not read that wrapper: tnt_ai_accept_value decomposes the same product into
# named rows so the tooltip can show them, adding each modifier row multiplied by
# tnt_gain_scale_unit_value (= max(0,offer)/100). Algebraically those rows sum to
#     offer * (100 + S) / 100        where S = tnt_deal_mod_sum_value
# with NO clamp anywhere. S is a sum of penalties that really can pass -100:
# opinion -100, hostile faith -35, foreign heritage -10, nemesis -50, threshold -40.
# At S = -235 the effective multiplier is -1.35, so every coin offered SUBTRACTED
# 1.35 points, monotonically. 1000 gold read -135; 2000 read -270.
#
# WHAT THIS ROW IS. Exactly the shortfall, and nothing else:
#     floor = unit * max(0, -(100 + S))
# Added to the headline it turns offer*(100+S)/100 into offer*max(0,(100+S))/100,
# which is what tnt_deal_mult_value has always computed. It is an algebraic
# identity, not a new rule - the headline stops disagreeing with the previews, with
# autobalance and with its own tooltip.
#
# THE PROPERTIES THAT SURVIVE, each of which someone will otherwise "fix" later:
#   * an empty treaty still reads EXACTLY 0 - unit is 0, so the floor is 0 too;
#   * opinion stays meaningful over its whole useful range - at S = -80 gold still
#     works, just at five times the price;
#   * contempt VOIDS gifts, it never INVERTS them - at S <= -100 more gold changes
#     nothing at all, which is the immersive reading of "he will not deal with you"
#     and is why no hard block at opinion < -99 is needed;
#   * marginal value of a gift is max(0,(100+S))/100 >= 0, so adding to the table
#     can never lower the headline again.
#
# SCOPE DISCIPLINE: evaluated on the CURRENT scope, deliberately unlike
# tnt_deal_mult_value's scope:actor dance. It must match the rows it corrects, and
# those - the seven tnt_relmod_* and tnt_threshold_value - rescue their own scopes
# internally (tnt_51_relation_values.txt:193-206). Reading actor here would let the
# correction and the rows disagree in exactly the interaction contexts where the
# whole scope problem lives.
#
# ORDER OF OPERATIONS: `min = 0` sits before the final multiply, and that is safe
# because unit >= 0 by construction - clamping before or after a non-negative
# factor gives the same number.
###############################################################################
tnt_deal_floor_value = {
	value = 100
	add = tnt_deal_mod_sum_value
	multiply = -1
	min = 0
	multiply = tnt_gain_scale_unit_value
}

# tnt_ai_unpaid_ask_value   -   V16, USER ITEM 2 (Q2-F1)
#
# WHAT IT IS: the pure trade delta MINUS the part of that delta the AI's own
# valuation model already says it is owed. In one sentence: what the letter takes
# ON TOP OF ITS OWN PRICING.
#
#   tnt_ai_unpaid_ask_value = tnt_balance_value + tnt_relation_mod_value
#
# The plus sign is not a typo. tnt_balance_value is gain - loss from the
# PARTNER's point of view, and tnt_relation_mod_value is signed the same way
# (positive = he likes you, so he will sign for less). Adding them therefore
# subtracts the discount a hostile partner demands, which is exactly the
# quantity the go/no-go wanted and never had.
#
# WHY IT HAD TO EXIST - THE MEASUREMENT, error.log of 2026-08-17, 5,185 TNTLOG
# lines, 29 composed letters:
#   * 19 of 29 letters (65.5%) never reached the player, and 17 of the 19 died
#     on ONE row in events\tnt_ai_events.txt: `tnt_balance_value <= 3`.
#   * tnt_balance_value = gain - loss EXACTLY on all 19 aborts (#1 82-30=52,
#     #6 110-55=55, #14 256-63=193, #18 254-0=254, #29 230-120=110).
#   * sign(rel) predicted delivery with 100% accuracy over all 29 letters: every
#     letter that ARRIVED had rel >= +1; every letter that ABORTED had rel <= 0.
#   * bal + rel over those 19 aborts is {-89, -7, 1,1,1,1,1,2,2,3,3,3,4,5,6,9}
#     - i.e. the refused surplus IS the relation premium and nothing more.
# THE MECHANISM, from the value definitions rather than from the correlation:
# tnt_ai_offer_settle_effect drives tnt_ai_accept_value to 1 (MARGIN = 1,
# CEILING = 1, tnt_37_ai_offer.txt), and accept = gain - loss + rel
# - thresh% * gain/100. Pinning accept at 1 therefore drives gain - loss to
# about 1 - rel; the very next row then refused the letter unless
# gain - loss <= 3. For any proposer with a negative relation row the pair was
# MATHEMATICALLY UNSATISFIABLE, so the mod was a friend-only diplomat - and
# every refused letter had already burnt the proposer's multi-year lock.
# The eight relation rows and the threshold are PERCENTAGES of the ask (each is
# multiplied by tnt_gain_scale_unit_value = tnt_gain_positive_value/100,
# tnt_50_values.txt:2514), which is why rel grows with whatever the settle just
# added and the two rows could never both be satisfied.
#
# WHAT IT IS NOT: it is not a second headline and nothing on screen reads it.
# It is a GO/NO-GO INSTRUMENT ONLY - one consumer, the OR at
# events\tnt_ai_events.txt. It carries no desc, deliberately: a desc-bearing
# value that no tooltip points at is dead weight, and tnt_balance_value's own
# ~30 item rows are still the detail layer for anything the GUI wants to show.
#
# `round = yes` at the top level, matching both inputs, so the comparison in the
# event is integer-against-integer. Two-term add/subtract with a top-level round
# is vanilla's own shape for a relative figure -
# GAME\common\script_values\05_bp2_hostage_values.txt:849-854
# (interaction_relative_hostage_value), cited above by tnt_balance_value itself.
###############################################################################
tnt_ai_unpaid_ask_value = {
	value = tnt_balance_value
	add = tnt_relation_mod_value
	round = yes
}


# --- relationship subtotal --------------------------------------------------
# Plain number, no desc: it is figure row 3 of the balance panel, "standing
# between you" (loc tnt_bd_relation). The eight parts are emitted as individual
# rows by tnt_ai_accept_value below, so this value must NOT carry desc of its own
# or the same numbers would be counted twice in one tooltip.
#
# This is the ONLY signed one of the four figures, and the only one that reaches
# tnt_ai_accept_value un-aggregated (as eight separate desc rows). The arithmetic
# still closes exactly, and here is the proof, because it is not obvious:
#   let G, L, T be the three OTHER figures. All three are rounded at their own
#   top level, so tnt_ai_accept_value sees integers for them. Write R for the raw
#   unrounded relation sum.
#     headline   = round( G - L + R - T )  =  G - L - T + round(R)
#                  (round(integer + fraction) = integer + round(fraction))
#     panel sum  = G - L + round(R) - T
#   The two are identical for every input. `round = yes` on THIS value is what
#   makes the printed figure equal round(R) rather than a truncation.
tnt_relation_mod_value = {
	value = 0
	add = tnt_relmod_opinion_value
	add = tnt_relmod_faith_value
	add = tnt_relmod_culture_value
	add = tnt_relmod_kin_value
	add = tnt_relmod_relation_value
	# NO DREAD ROW - see the note in tnt_ai_accept_value below. The panel's figure
	# and the headline must sum from the same list, so it is dropped in both places
	# or in neither.
	add = tnt_relmod_war_value
	add = tnt_relmod_ally_value
	# THE SEVEN ROWS ARE PERCENTAGES; THIS FIGURE IS POINTS. The panel's four figures
	# must sum to the headline, and the headline scales each row by one per cent of
	# the offer - so this sum is scaled once, here, by the same unit. With an empty
	# treaty the figure reads 0, which is the whole point of the model.
	#
	# *** V17 - THIS MULTIPLY IS THE ROOT CAUSE OF THE AI LETTER'S RUNAWAY ASK, AND
	# *** THE FIX IS DELIBERATELY NOT LANDED HERE. READ THIS BEFORE TOUCHING EITHER.
	# Because this figure is a PERCENTAGE OF THE PACKAGE while the settle's target is
	# a fixed accept = +1, the settle's own fixed point is
	#     gain = (1 + loss) / (1 + k - thresh/100)      where k = rel/gain < 0
	# so as k approaches -1 the denominator approaches zero and the ask DIVERGES;
	# past -1 the sweeten loop cannot converge at all. Measured, error.log
	# 2026-08-17: the empty-table letter the user photographed sat at k = -0.97, a
	# 33x inflation - which is why it asked for gold AND prestige AND piety at once,
	# the loop walking its whole ladder chasing a target that receded as it
	# approached. One arch19 letter reached k = -1.17 and landed at accept = 0, the
	# run's only such abort. Four honest arch16 marriages sat at -0.52 .. -0.62 and
	# were priced out of existence.
	# THE BOUNDED FIX IS ONE ROW: `min = -60` between the seven adds and this
	# multiply, which caps the inflation multiplier at 1/(1-0.60) = 2.5x and makes a
	# 300-point ask unreachable by construction rather than by a cap.
	# WHY IT IS NOT HERE: this value is FIGURE ROW 3 OF THE PLAYER'S BALANCE PANEL
	# (see the header above - the four figures must sum exactly to the headline), so
	# clamping it changes a number the player has been reading for many rounds. That
	# is a design decision for the user, not a drive-by edit, and it is recorded as
	# OPEN in _docs\99-BACKLOG.md section A3 and in CLAUDE.md.
	# AND DO NOT CLAMP ONLY ON THE LETTER PATH: the window's figure and the letter's
	# figure would then disagree across the counter-offer click, which is precisely
	# the defect events\tnt_ai_events.txt was written to close. A window-neutral
	# alternative exists (stash the compose-time gain and bound the sweeten `while`
	# against 2.5x it) and is written up in the same backlog section.
	# WHAT V17 DID INSTEAD, so the symptom is bounded meanwhile: the go/no-go in
	# events\tnt_ai_events.txt gained a STANDING FLOOR,
	# `tnt_deal_mod_sum_value >= -35`, which refuses the pairs whose k the settle
	# cannot price - all 12 of the run's runaway letters had a standing of -47.9 or
	# worse and the closest surviving letter sat at -23. That bounds the damage; it
	# does not bound k.
	multiply = tnt_gain_scale_unit_value
	round = yes
}

# ===========================================================================

# Iterations 0-1 built this value as a FLOOR: `value = 15` … `min = 5`, plus +40

#    `value = 0`, `min = 0`. For a partner of ordinary personality and equal or
#    lower rank it returns 0 and the row prints 0. The headline is then
#    literally (gain - loss + standing), i.e. the same quantity vanilla prints,
#    on the same scale — which is requirement 2 of the fix.
# 3. Because it is 0 by default, "the number went positive" and "he agrees" are
#    still the same statement, and the number is now also directly comparable to

#    hold at once, which is only possible because the default is zero. A

# ===========================================================================
# THE BODY, retuned onto vanilla's friction band
# ===========================================================================
#   value = 0                        vanilla's stated default (:758 above)

#   + ai_boldness   x 0.05           was 0.20
#   - ai_rationality x 0.05          was 0.10

#   + 20   he outranks us by two or more   with a count, and an emperor still less
#   min = 0    max = 40

# -15..+20 and the whole value lands in 0..40 — inside vanilla's own friction band
# (-10 demand_courtier … -50 offer_vassalization) and on its ladder
# (00_ai_values.txt:22-34: very_low 10 / low 20 / medium 35).
# `min = 0` and not `min = -15`: a partner may not PAY the player for the privilege
# of being asked, and a negative row under a label that reads "their price for
# agreeing" would be a lie. Generosity reaches the headline through the standing
# rows, where it belongs.
#
# The two-tier pride ladder replaces iteration 1's flat +40. It is driven by
# tnt_tier_edge_value, which is (player tier - partner tier), so < 0 means the
# partner is the higher-ranked man. Two literals against one named value — the
# R7-legal shape, never a variable-to-variable comparison.
#
# ai_greed / ai_boldness / ai_rationality as script-value fields:
#   GAME\common\script_values\00_activity_values.txt:11,81,87
#   GAME\common\character_interactions\00_alliance.txt:2034 (`add = ai_greed`, and
#   note that vanilla reads them INSIDE a live ai_accept, which is our case too)
#
# The balance panel may read this value READ-ONLY (amendment A-3 restates
# acceptance check 17 to allow exactly that, and nothing more).
# `round` comes AFTER `min`, so the printed figure and the summed figure are the
# same integer. See the arithmetic proof above tnt_relation_mod_value.

tnt_threshold_value = {
	value = 0
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	scope:tnt_p ?= {
		add = {
			value = ai_greed
			multiply = 0.1
		}
		add = {
			value = ai_boldness
			multiply = 0.05
		}
		subtract = {
			value = ai_rationality
			multiply = 0.05
		}
	}
	if = {
		limit = { tnt_tier_edge_value <= -2 }
		add = 20
	}
	else_if = {
		limit = { tnt_tier_edge_value < 0 }
		add = 10
	}
	min = 0
	max = 40
	round = yes
}

# THE VERDICT — AND, AS OF v2, THE ONLY NUMBER THE PLAYER EVER SEES.
# The second and last desc-bearing value.
#
# ===========================================================================
# USER ITEM 1.2, THE WHOLE FIX, IN ONE PLACE  (30-V2-DESIGN §5)
# ===========================================================================
# The complaint, verbatim: «как только очки в плюсе — это должно означать
# автосогласие, сейчас же — нужно отвести очки дальше плюса, чтобы получить
# согласие: очки за мнение и т.п. должны считаться сразу.»
#
# The v1 defect was not a bug, it was a deliberate and wrong ruling
# (10-CONTRACT.md §11 row 3): the headline number, the tilting scales and the
# main tooltip all showed tnt_balance_value — the pure trade delta — while the
# verdict icon and the event's option triggers tested tnt_ai_accept_value. The
# gap between them is exactly (threshold - relations), typically 20..60 points,
# so the player pushed the visible number well past zero and was still refused.

# v2 reverses the DISPLAY half of that ruling (amendment A-3). Every headline
# widget now reads THIS value:
#     number    tnt_types.gui   text = "[TntSV('tnt_ai_accept_value')|+=0]"
#     tooltip                   datacontext = "[TntBreakdown('tnt_ai_accept_value')]"

#     verdict                   unchanged — it already read this value

# (Line numbers deliberately dropped from this list: tnt_types.gui was rebuilt for
# items 3.2/3.3/3.4 and every one of them had rotted. Grep the widget names.)
#
# THE ROW LIST IS AN EXACT DECOMPOSITION, AND THAT IS THE POINT.

#     row 1  tnt_bd_gain       tnt_gain_total_value        +   "worth to them"

#                              (reaches this value as its eight named parts)
#     row 4  tnt_bd_threshold  tnt_threshold_value         -   "their price for agreeing"
#     ===    headline          tnt_ai_accept_value
# Row1 - Row2 + Row3 - Row4 == the headline, exactly, for every input. All four
# aggregates carry `round = yes`; the proof that the eight-rows-vs-one-figure
# asymmetry in row 3 still closes is written out above tnt_relation_mod_value.
# A tooltip that does not add up is worse than no tooltip at all.
#
# WHAT WAS REMOVED: the single `add = { value = tnt_balance_value desc = tnt_bd_trade }`
# row. It is replaced by the two column totals so that the top-level tooltip reads
# as the same four figures the panel prints. tnt_balance_value keeps all ~30
# item-level rows and is still reachable as the detail layer (see its own header).
# Nothing is lost and nothing is double-counted: the item rows live INSIDE
# tnt_gain_total_value / tnt_loss_total_value, which carry no desc of their own,
# so contract §4 rule 3 ("exactly two values carry desc") still holds.
# Loc key tnt_bd_trade is now unused and should be deleted from both .yml files.
#
# ===========================================================================
# v3 ITERATION 2 — WHAT THIS VALUE NOW READS, AND WHY IT MATCHES VANILLA
# ===========================================================================
# Nothing about the SHAPE of this value changed in iteration 2. The five rows are
# the same five rows and they still sum exactly to the headline. What changed is
# what the summands MEAN:
#   * every per-item value is now priced in RAW VANILLA ACCEPTANCE POINTS — see the
#     CALIBRATION block at the top of this file for the four currency unit prices
#     and the per-term anchor index;
#   * the eight standing rows are NOT acceptance points any more: since V4 each one
#     is a PERCENTAGE of the offer, applied through tnt_gain_scale_unit_value, and
#     opinion runs at x1.00 raw, +-100, NOT x0.75 (tnt_51_relation_values.txt:210-222);
#   * tnt_threshold_value is centred on ZERO instead of floored at 5, so it no
#     longer applies a constant 15..95 penalty to every deal ever composed. Read
#     its own header — that is the fix the user asked for, in full.
# THE OLD "+13 AGAINST VANILLA'S +12" PARITY CLAIM THAT STOOD HERE IS RETRACTED. It
# was pre-V4 arithmetic that summed the standing rows as FLAT points, and measuring
# the window against it is what has made this mod look broken every round since.
# The retraction is written out at tnt_52_marriage_values.txt:1894-1896 and the
# own-scale choice behind x1.00 at :1910-1913. A one-term treaty pays a standing row
# at row x offer/100, so opinion +20 on a 17-point marriage is about +3, not +15.
#
# The threshold enters as a negative row, so the ONLY acceptance test
# anywhere in this mod is `tnt_ai_accept_value > 0`. Exactly 0 declines — proven
# twice in vanilla:
#   GAME\localization\english\interactions_l_english.yml:23
#     ANSWER_SUM_NEGATIVE:0 "Total: $VALUE|=+0$ (will only accept if total is positive)"
#   GAME\gui\interaction_templates.gui:3089  GreaterThan_CFixedPoint( …GetAcceptanceValue, 0 )
# That test is unchanged and must stay strictly greater-than-zero.
#
# All eight relationship rows are emitted unconditionally, even at 0, so the
# tooltip has a stable row count frame to frame and needs no extra per-frame
# triggers (contract §4.E). The two column-total rows are likewise unconditional.
#
# The gain and loss rows nest: hovering one opens tnt_gain_total_value's parts,
# because widget_value_breakdown_tooltip recurses
# (GAME\gui\shared\value_breakdown.gui:1942-1945, `recursive = yes`).
###############################################################################
tnt_ai_accept_value = {
	value = { value = 0  desc = tnt_bd_base }
	# --- figure row 1: everything the partner receives ---------------------
	add = { value = tnt_gain_total_value  desc = tnt_bd_gain }
	# --- figure row 2: everything the partner hands over -------------------
	# `multiply = -1` inside the desc-bearing add block is the sanctioned
	# negative row; verbatim vanilla at
	# GAME\common\script_values\00_activity_values.txt:286-290.
	add = { value = tnt_loss_total_value  multiply = -1  desc = tnt_bd_loss }
	# --- figure row 3: the standing between the two rulers -----------------
	# Emitted as its eight named parts, not as tnt_relation_mod_value, so the
	# player can see WHICH part of the relationship is carrying the deal. The
	# panel prints their rounded sum as one figure; the arithmetic closes.
	# EVERY ROW IS A PERCENTAGE OF THE OFFER, multiplied by one per cent of it. This
	# is what makes an empty treaty read EXACTLY 0 for every partner in the game:
	# with nothing on the table the unit is zero, and zero times any relationship is
	# zero. The rows keep the numbers they always had - the numbers are now read as
	# per cent. Full argument at tnt_gain_scale_unit_value.
	add = { value = tnt_relmod_opinion_value   multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_opinion }
	add = { value = tnt_relmod_faith_value     multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_faith }
	add = { value = tnt_relmod_culture_value   multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_culture }
	add = { value = tnt_relmod_kin_value       multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_kin }
	add = { value = tnt_relmod_relation_value  multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_relation }
	# THE PASSIVE DREAD ROW IS GONE, AND IT IS A DOUBLE-COUNT THAT V4 CREATED.
	# tnt_relmod_dread_value paid up to +50 simply for being feared, and expansion 1
	# then added the threat option, which prices the very same fear a second time -
	# up to 150 for a click. Being frightening now does nothing until the player USES
	# it, which is exactly what the user's ruling asks for: "the threat is an option
	# that gives points". The value keeps its definition and its localization key so
	# nothing dangles; it simply has no caller.
	add = { value = tnt_relmod_war_value       multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_war }
	add = { value = tnt_relmod_ally_value      multiply = tnt_gain_scale_unit_value  desc = tnt_relmod_ally }
	# --- figure row 4: what he wants on top of a merely fair trade ---------
	# THE THRESHOLD IS A PERCENTAGE TOO, and it had to become one or the window would
	# still not open at zero: it runs 0..40 and used to be subtracted flat, so a
	# greedy partner taxed an empty treaty by up to 40 points before a single term
	# existed. Read as per cent it says the honest thing instead - a greedy, bold,
	# unreasoning ruler values what you offer him up to 40% below its worth.
	add = { value = tnt_threshold_value  multiply = tnt_gain_scale_unit_value  multiply = -1  desc = tnt_bd_threshold }
	# --- figure row 4b: THE CLAMP THE ROWS ABOVE DO NOT HAVE ---------------
	# Zero in every ordinary deal, and it must be emitted unconditionally anyway so
	# the tooltip's row count never changes under the player. It is non-zero only
	# when the rows above sum past -100, where without it each further coin offered
	# made the headline WORSE. Full argument at tnt_deal_floor_value.
	add = { value = tnt_deal_floor_value  desc = tnt_bd_floor }
	# --- figure row 5: NAKED PRESSURE (V4 expansion 1) ---------------------
	# Its own row, and NOT a member of tnt_gain_total_value, for one reason that
	# must not be undone: fix 5 made opinion a multiplier on the gift total, so a
	# partner who hates the player values his gifts at nothing. Fear is the
	# instrument for exactly that partner, so it has to sit outside the multiplier.
	# The full reasoning and the calibration are in tnt_57_threat_values.txt.
	add = { value = tnt_val_threat_p_value  desc = tnt_bd_threat_p }
	# --- figure row 5b: A HOOK YOU ALREADY HOLD (V4 item 2) ----------------
	# Outside the gift total for the same reason the threat is: leverage has to keep
	# working on a ruler whose every other modifier is negative. Priced in
	# tnt_59_usehook_values.txt, 45 for a favour called in and 120 for blackmail-grade
	# leverage; the panel prints it together with the threat as "Pressure".
	add = { value = tnt_val_usehook_p_value  desc = tnt_bd_usehook_p }
	# --- figure row 5c: A HOOK THE PARTNER HOLDS ON US (V4 item A2) ---------
	# NEGATIVE by construction: a debt he can call in makes him more demanding, not more
	# willing, so at the same terms he is less satisfied. His composer then asks for more,
	# which is what calling in a debt looks like from the other side. Full argument at the
	# value's definition in tnt_59_usehook_values.txt.
	add = { value = tnt_val_usehook_r_value  desc = tnt_bd_usehook_r }
	round = yes
}

###############################################################################
# THE TWO-SIDED BAR — the third rendering of the deciding value (item 1.2)
#
# The bar must not be able to disagree with the number beside it, so its DIRECTION
# comes from the authoritative, once-rounded tnt_ai_accept_value. Its two halves
# still measure how much is pushing the partner towards yes and no:
#
#   tnt_accept_pos_value  - the visible magnitude pushing him TOWARDS yes
#   tnt_accept_neg_value  - the visible magnitude pushing him TOWARDS no
#
# Those magnitudes are deliberately NOT another source of truth for the verdict.
# tnt_deal_floor_value and threat can be fractional, while relation and threshold
# are rounded independently on the two sides and the headline rounds their complete
# sum once. Consequently `pos - neg` can differ from the headline by a small rounding
# residue. Rounding those components here is not cosmetic: the offline model found
# cases where doing so changes acceptance itself.
#
# THE PROPERTY THAT MATTERS is therefore enforced directly below:
#   headline == 0  =>  ratio == exactly 50
#   ratio > 50     <=> headline > 0 <=> HE ACCEPTS.
# The sum `pos + neg + 2` remains the scale, so a one-point margin moves the bar less
# on a large treaty than on a small one. When `pos - neg` does equal the headline,
# the formula is algebraically identical to the old `(pos + 1) / (pos + neg + 2)`.
# The bar crossing the halfway mark IS the verdict flipping. That is user item 1.2
# expressed as a bar instead of as a number.
#
# DEVIATION FROM 30-V2-DESIGN §5.1, DELIBERATE AND FLAGGED — AND RESOLVED IN
# BUILD 2. §5.1's table row for tnt_bar_ratio_value says "unchanged — the bar keeps
# meaning 'how much of the deal is you giving vs them giving'". That conflicts with
# the build order for this file, which requires the bar to derive from the value
# that decides, and with the build-2 acceptance check "headline, scales, bar,
# verdict and breakdown all derive from tnt_ai_accept_value".
# RESOLUTION: the GUI now binds the two-sided bar to tnt_verdict_ratio_value
# (gui\tnt_types.gui, type tnt_balance_bar, both layoutstretchfactor_horizontal
# expressions). tnt_bar_ratio_value below is UNTOUCHED, still means the pure trade
# ratio, and now has no reader — which this header already said was harmless, and
# it remains the ready-made fallback for §8 R-9: swapping the two names back is a
# two-line edit in one file.
# The loc key tnt_scale_note is reworded to describe the 50-mark rule, in both
# languages.
###############################################################################
# NO min / max on either half, deliberately. Neither half can go negative:
# tnt_gain_total_value and tnt_loss_total_value are sums of values that
# are all >= 0 (contract §4 rule 5), tnt_threshold_value carries min = 0, and each
# relation branch only ever adds magnitude to its own side. So pos >= 0 and
# neg >= 0 by construction, and the divisor below has its own min = 1.
#
# v3 ITERATION 2 — the threshold's floor moved from 5 to 0, so `neg` can now be a
# genuine 0 for an empty table with an easy-going partner. The `+1 / +2` smoothing
# in tnt_verdict_ratio_value below already covers that case and puts the bar at
# exactly 50, which is the right reading: nothing on the table, no verdict either
# way. Do NOT reintroduce a floor here to "protect" the division.
tnt_accept_pos_value = {
	value = 0
	add = tnt_gain_total_value
	if = {
		limit = { tnt_relation_mod_value > 0 }
		add = tnt_relation_mod_value
	}
	# V4: NAKED PRESSURE BELONGS ON THE "YES" SIDE, and it was missing here from the
	# moment the threat was added - so the two-sided bar disagreed with the headline
	# by exactly the threat's worth. Both terms are >= 0 by construction
	# (tnt_57_threat_values.txt, tnt_59_usehook_values.txt), so they need no branch.
	add = tnt_val_pressure_p_value
	# V5 item 8: the multiplier floor belongs on the "yes" side, because that is
	# where the rows it corrects live. It is >= 0 by construction (tnt_deal_floor_value
	# ends in min = 0 before a non-negative multiply), so it needs no branch and
	# cannot break the pos >= 0 invariant this header insists on. Without it the bar
	# would disagree with the headline by exactly the voided-gift amount.
	add = tnt_deal_floor_value
}

tnt_accept_neg_value = {
	value = 0

# --- 0..100 rendering of the DECIDING value, for the two-sided bar ------------

#   ratio = 50 + 50 * headline / (pos + neg + 2)
# so a zero headline is exactly 50 even when independent component rounding leaves
# pos != neg. Do not replace the headline with `pos - neg`; that was the measured bug.

tnt_verdict_ratio_value = {
	value = 50
	add = {

	}
	min = 0
	max = 100
