# USER ITEM 2.3 (hook tiers) and USER ITEM 2.5 (the vassal contract template)
#
# Owner: hooks-contracts.  26 values:
#     §1   4  hooks        — 2 tier prices + 2 "can a hook still be granted"
#     §2   4  direction    — which side swears fealty, the sign, and the two
#                            government tests that follow from it
#     §3   5  legality     — is each gated obligation settable right now
#     §4   9  prices       — one per obligation, SIGNED FROM THE PARTNER'S SIDE
#     §5   4  display      — the two printable level indices, the sheet total and
#                            the changed-row count
#
# ---------------------------------------------------------------------------
# §0.1  THE FILE'S OWN RULES, inherited unchanged from tnt_50_values.txt
# ---------------------------------------------------------------------------
# 1. root is ALWAYS the player. GetScriptValueBreakdown supplies root and
#    nothing else, so every value here reads ONLY root and var: values (R9).
# 2. The partner is reached through contract R0.4's prologue and never as a GUI
#    scope:   var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
#    Proof that this works inside a script value:
#    GAME\common\script_values\00_scheme_values.txt:2434-2437.
#    D4: `tnt_p` is the TEMPORARY name used by ~60 value prologues; the
#    PERMANENT deal scope is tnt_deal_partner. Never introduce a third user of
#    either name (30-V2-DESIGN §9 D4).
# 3. Never compare two variables (R7). Every test below is
#    var-against-literal or named-value-against-literal.
# 4. No `desc =` on any value in this file. Only tnt_balance_value and
#    tnt_ai_accept_value carry desc (contract §4 rule 3). The desc ROWS for the
#    nine obligation prices live in tnt_balance_value, keys tnt_bd_ob_* — and
#    per R10 none of those keys may contain the $VALUE$ token, because the
#    breakdown widget renders the number in its own right-aligned column
#    (GAME\gui\shared\value_breakdown.gui:1935-1955).
# 5. Every object-valued variable read is guarded by `exists =` or `?=` (R13).
#
# ---------------------------------------------------------------------------
# §0.2  THE ONE PLACE THIS FILE BREAKS A CONTRACT RULE, AND WHY
# ---------------------------------------------------------------------------
# 10-CONTRACT §4 rule 5 says every per-item value returns >= 0 and the sign is
# applied once, by the aggregate. THE NINE OBLIGATION PRICES IN §4 ARE SIGNED.
# They have to be: a high tax is a COST to the subject and a GAIN to the liege,
# and both sit in the same deal. 30-V2-DESIGN amendment A-2 (from §2 C-7, report
# 41 W-11) grants exactly this exemption and states the consequence:
#
#     "each obligation gets its own explicit row in tnt_balance_value WITHOUT
#      the aggregate's multiply = -1, and rule 5 is restated as: all per-item
#      values of the twelve v1 items return >= 0; the nine obligation values are
#      signed and are added directly"
#
# ---------------------------------------------------------------------------
# §0.3  WHOSE SIDE THE SIGN IS ON — READ THIS BEFORE TOUCHING §4
# ---------------------------------------------------------------------------
# tnt_ai_accept_value answers ONE question: would THE PARTNER accept? So every
# row in it must be signed from the partner's point of view. Vanilla's own
# obligation prices (00_character_interactions.txt:1029-1053) are written from
# the would-be VASSAL's point of view, and vanilla mirrors them by hand for the
# liege side (:1657-1668, the same numbers with the sign flipped).
#
# We cannot mirror by hand, because ONE variable set serves both directions
# (the nine tnt_ob_* carry no side suffix — T11 forbids both sides swearing
# fealty, so only one contract can ever be on the table). Instead each price is
# written once from the SUBJECT's point of view and multiplied by
# tnt_ob_sign_value:
#
#   tnt_vassal_p = 1  the PLAYER swears fealty  -> the player is the subject,
#                     the partner is the liege. A high tax on the player pleases
#                     the partner.                                sign = -1
#   tnt_vassal_r = 1  the PARTNER swears fealty -> the partner is the subject.
#                     A high tax on the partner is his own burden. sign = +1
#   neither           nothing on the table.                        sign =  0
#
# CONSEQUENCE FOR THE BALANCE INTEGRATOR: the nine values below are ALREADY
# correctly signed for tnt_ai_accept_value. Add them with a plain
#     add = { value = tnt_val_ob_tax_value  desc = tnt_bd_ob_tax }
# and NEVER with a multiply. See NOTES3-hooks-contracts.md for the exact rows.
#
# ---------------------------------------------------------------------------
# §0.4  WHY THE LEGALITY VALUES OF §3 EXIST AT ALL
# ---------------------------------------------------------------------------
# Report 41 W-9: it is UNKNOWN whether vassal_contract_set_obligation_level
# enforces the level's own is_valid or the type's is_shown, and vanilla never
# depends on it — it duplicates every gate in the interaction instead
# (religious_exemption's is_valid = { scope:recipient.faith != scope:actor.faith },
# 00_character_interactions.txt:1276-1278). So we duplicate them too, three times
# over, each layer catching what the one before it cannot:
#   * §3 here          -> the GUI greys the row out (cheap, one value read; a
#                         GetScriptedGui in a per-row `enabled` is what R11 is
#                         about, and a script value costs a fraction of it)
#   * tnt_22c_*.txt    -> the setter refuses to write the variable at all
#   * tnt_36_*.txt     -> the apply leg refuses to emit the line
# A gate that only lives in the GUI is not a gate: the variable survives a
# partner change, a conversion and a save/load.
#
# GATES, WITH THE EXACT VANILLA SOURCE OF EACH:
#   religious_rights          subject.faith != liege.faith

# --- 1.1 THE TIER PRICE LADDER ----------------------------------------------
# tnt_hook_p / tnt_hook_r stopped being 0/1 flags and are now TIER INDICES:
#   0 (or absent) none · 1 weak favour · 2 strong · 3 eternal
# (30-V2-DESIGN §3.2. The coordinated-edit list is W-12 in that section.)
#
# v3 ITERATION 2 — 20 / 50 / 100, WHICH IS NOW VANILLA'S LADDER VERBATIM FOR THE
# FIRST TWO RUNGS. It was 30 / 70 / 120: the same anchors, but multiplied up into
# the old "100 points is a year of the partner's income" currency. That currency is
# gone (tnt_50_values.txt, CALIBRATION block), so the scaling step goes with it and
# vanilla's own two figures are used as they stand:
#     +20 weak   00_scheme_scripted_modifiers.txt:615-621  (scope:offer_hook)
#     +50 strong 00_scheme_scripted_modifiers.txt:622-628  (scope:offer_hook_strong)
# THE THIRD RUNG (eternal, never consumed) IS STILL INVENTED — vanilla offers only
# two tiers of hook — but it is now +100, which keeps the 20 -> 50 -> 100 geometric
# feel AND lands exactly on vanilla's price for SPENDING a weak hook you already
# hold (00_marriage_scripted_modifiers.txt:12-13, `add = 100`). A hook that can be
# spent forever being worth one guaranteed spend is a defensible floor, and the
# parity table recommends this number by name.
#
# NOT the +100/+200 ladder of 00_marriage_scripted_modifiers.txt:11-22: that is
# the price of SPENDING a hook you already hold to coerce somebody, a different
# mechanic. 30-V2-DESIGN §2 C-1 settles it, and report 41's own 85/210/300 table
# is explicitly withdrawn there.
#
# THESE ARE NOT THE VALUES THE BALANCE READS. tnt_50_values.txt owns
# tnt_val_hook_p_value / _r_value (flat 85 today, referenced by
# tnt_gain_total_value, tnt_loss_total_value and tnt_balance_value). The
# integration line asks its owner to replace each three-line body with
# `add = tnt_val_hook_tier_p_value`, so the ladder lives in exactly one file and
# no consumer moves. See NOTES3-hooks-contracts.md.
#
# `>= 3` rather than `= 3` on the last rung: the setters clamp to 3, but a value
# that silently prices nothing when a variable goes out of range is the worse
# failure of the two.
tnt_val_hook_tier_p_value = {
	value = 0
	if = {
		limit = {
			exists = var:tnt_hook_p
			var:tnt_hook_p = 1
		}
		add = 20
	}
	else_if = {
		limit = {
			exists = var:tnt_hook_p
			var:tnt_hook_p = 2
		}
		add = 50
	}
	else_if = {
		limit = {
			exists = var:tnt_hook_p
			var:tnt_hook_p >= 3
		}
		add = 100
	}
	# A promised hook is on its giver, not on the receiving partner.
	if = {
		limit = { tnt_scaled_valuation_enabled_value > 0 }
		if = {
			limit = { exists = var:tnt_hook_p var:tnt_hook_p > 0 }
			multiply = tnt_scaled_hook_leverage_factor_value
		}
	}
}

tnt_val_hook_tier_r_value = {
	value = 0
	if = {
		limit = {
			exists = var:tnt_hook_r
			var:tnt_hook_r = 1
		}
		add = 20
	}
	else_if = {
		limit = {
			exists = var:tnt_hook_r
			var:tnt_hook_r = 2
		}
		add = 50
	}
	else_if = {
		limit = {
			exists = var:tnt_hook_r
			var:tnt_hook_r >= 3
		}
		add = 100
	}
	if = {
		limit = { tnt_scaled_valuation_enabled_value > 0 }
		if = {
			limit = { exists = var:tnt_hook_r var:tnt_hook_r > 0 }
			var:tnt_partner ?= {
				multiply = tnt_scaled_hook_leverage_factor_value
			}
		}
	}
}


# --- 1.2 CAN A HOOK STILL BE GRANTED IN THIS DIRECTION? ---------------------
# 1 = yes, 0 = the receiver ALREADY holds a hook over the giver.
#
# WHY THIS IS NOT OPTIONAL (report 41 W-13). Our apply leg goes through
# add_hook_if_possible_default_length_effect, whose whole body is
#     if = { limit = { can_add_hook = { … } }  add_hook = { … } }
# (GAME\common\scripted_effects\00_hook_effects.txt:28-41). That guard SWALLOWS
# FAILURE SILENTLY, so without a gate the player pays for a term that quietly
# never applies. Vanilla gates the same case in the interaction instead:
#     is_valid = { NOT = { scope:recipient = { has_hook = scope:actor } } … }
# (GAME\common\character_interactions\00_invite_agent_to_scheme.txt:606-615).
#
# DIRECTION, and it is the one thing to get right here. The side that GIVES this
# term ends up OWING: the RECEIVER gains the hook, the GIVER is the one hooked
# (the shipped comment at tnt_32_apply.txt:714-722 spells this out, citing
# GAME\common\character_interactions\00_grant_titles_interaction.txt:1065-1077).
#   _p : the player grants a hook on himself -> the receiver is the PARTNER, so
#        the test is "does the partner already hold a hook on the player".
#   _r : mirrored.
#
# Default 1 with a -1 correction, rather than 0 with a +1: if the partner is
# missing or dead the value reads 1, the row stays offerable and the apply-time
# can_add_hook is the last word. A gate that locks the player out when it cannot
# answer is worse than one that defers.
#
# THE NESTING IS THE GUARD, and it is the shipped idiom of this mod rather than a
# new one: an outer `if = { limit = { exists = scope:tnt_p } }` decides whether
# the inner test is evaluated AT ALL, and the inner test lives inside an
# `add = { }` block, exactly as the currency values put their trait riders inside
# one (tnt_53_currency_values.txt:289-302). Writing both tests as two rows of one
# limit would NOT be equivalent: a limit is an AND-list with no promised
# evaluation order, so `exists` on one row cannot be relied on to keep the scope
# reference on the next row from being resolved.
tnt_hook_free_p_value = {
	# NO ROOT IN AN INTERACTION'S on_accept, so the value names the scope it stands on.
	# Full argument at tnt_52_marriage_values.txt:823-839. Guarded, because a parent
	# value or effect may already hold tnt_me and re-saving it is an error in itself.
	if = {
		limit = { NOT = { exists = scope:tnt_me } }
		if = {
			limit = { exists = scope:actor }
			scope:actor = { save_temporary_scope_as = tnt_me }
		}
		else = { save_temporary_scope_as = tnt_me }
	}
	value = 1
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = { exists = scope:tnt_p }
		add = {
			value = 0
			# the partner is the RECEIVER on this side: does he already hold one?
			if = {
				limit = { scope:tnt_p ?= { has_hook = scope:tnt_me } }
				add = -1
			}
		}
	}
}

tnt_hook_free_r_value = {
	value = 1
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = { exists = scope:tnt_p }
		add = {
			value = 0
			# the PLAYER is the receiver on this side
			if = {
				limit = { has_hook = scope:tnt_p }
				add = -1
			}
		}
	}
}

# §2  WHICH SIDE SWEARS FEALTY — USER ITEM 2.5
#
# The nine tnt_ob_* variables carry NO side suffix (30-V2-DESIGN §1 row 2.5:
# "T11 already forbids both sides swearing fealty, so only one contract can ever
# be edited"), so every consumer has to ask the direction separately. These
# three values are the single place that question is answered.
#
# Deliberately written from the two tnt_vassal_* variables directly and NOT from
# each other, so that no value here compares one script value with another (R7)
# and each can be read in isolation.
###############################################################################

# 0 = no fealty on the table · 1 = the PLAYER swears · 2 = the PARTNER swears.
#
# BUILD 3: NOW LIVE, with one consumer, and not the one this header used to claim.
# It said "read by the panel's three explanatory lines"; it was not -
# gui\tnt_panel_contract.gui drives those from TntOn('tnt_vassal_p') /
# ('tnt_vassal_r') directly, which is one variable read instead of a script-value
# evaluation and is the cheaper answer to the same question.
# THE REAL CONSUMER is the nine obligation rows of tnt_balance_value
# (tnt_50_values.txt), where each limit reads `tnt_ob_dir_value > 0` beside its
# `exists = var:tnt_ob_<x>`. Switching the fealty toggle off leaves the nine
# tnt_ob_* variables behind on purpose (see the residue note at the end of §4), and
# tnt_ob_sign_value goes to 0 with the toggle - so without this guard the player's
# breakdown would print up to nine "0" rows for a contract nobody is signing.
# Do NOT add this value to any aggregate: it is an enum, not a price.
tnt_ob_dir_value = {
	value = 0
	if = {
		limit = {
			exists = var:tnt_vassal_p
			var:tnt_vassal_p > 0
		}
		add = 1
	}
	else_if = {
		limit = {
			exists = var:tnt_vassal_r
			var:tnt_vassal_r > 0
		}
		add = 2
	}
}

# -1 · +1 · 0 — see §0.3. Multiplied into all nine prices of §4.
tnt_ob_sign_value = {
	value = 0
	if = {
		limit = {
			exists = var:tnt_vassal_p
			var:tnt_vassal_p > 0
		}
		add = -1
	}
	else_if = {
		limit = {
			exists = var:tnt_vassal_r
			var:tnt_vassal_r > 0
		}
		add = 1
	}
}

# 1 when the SUBJECT of the pending contract is feudal.
# This is the gate on ten of the eleven feudal_vassal contract types: setting
# feudal_government_taxes on a clan, tribal or administrative vassal names a
# type that is not in that subject's contract group and writes error.log.
# Vanilla applies exactly this guard before touching any feudal obligation
# (GAME\common\scripted_effects\00_interaction_effects.txt:2150-2153, with the

tnt_ob_feudal_value = {
	value = 0
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = {
			exists = var:tnt_vassal_p
			var:tnt_vassal_p > 0
			government_has_flag = government_is_feudal
		}
		add = 1
	}
	else_if = {
		limit = {
			exists = var:tnt_vassal_r
			var:tnt_vassal_r > 0
			scope:tnt_p ?= { government_has_flag = government_is_feudal }
		}
		add = 1
	}
}

# §3  IS EACH OBLIGATION LEGAL RIGHT NOW — seven gates
#
# 1 = settable · 0 = not. See §0.4 for why these exist and §0.5 for the proof of
# every trigger used. Each one folds in the government test, so a consumer never
# has to remember to ask both questions.
#
# council_rights and war_declaration_rights have NO gate of their own in vanilla,
# so their availability IS tnt_ob_feudal_value and they get no value here.
###############################################################################

# religious_rights — the "religious protection" the user asked for by name.
# Vanilla level key religious_rights_protected, index 1, score 3 — the joint
# highest score in the whole feudal group (special_contracts.txt:332-350).
# Available to feudal AND clan subjects (both groups carry the type), and only
# when the two faiths actually differ.
tnt_ob_relig_ok_value = {
	# NO ROOT IN AN INTERACTION'S on_accept, so the value names the scope it stands on.
	# Full argument at tnt_52_marriage_values.txt:823-839. Guarded, because a parent
	# value or effect may already hold tnt_me and re-saving it is an error in itself.
	if = {
		limit = { NOT = { exists = scope:tnt_me } }
		if = {
			limit = { exists = scope:actor }
			scope:actor = { save_temporary_scope_as = tnt_me }
		}
		else = { save_temporary_scope_as = tnt_me }
	}
	value = 0
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = {
			OR = {
				tnt_ob_feudal_value > 0
				tnt_ob_clan_value > 0
			}
			# `exists` does the LOGICAL job (a limit is an AND-list, so a missing
			# partner falsifies the whole row) and `?=` does the SAFETY job (no
			# dotted read of a scope that may not resolve). Both are needed; see
			# the longer note on tnt_ob_revoke_ok_value below.
			exists = scope:tnt_p
			NOT = { scope:tnt_p ?= { faith = scope:tnt_me.faith } }
		}
		add = 1
	}
}

# title_revocation_rights — vanilla's is_shown, simplified without changing it.
# Verbatim vanilla (special_contracts.txt:523-533):
#     OR = { subject.faith = liege.faith
#            NOR = { subject.faith = liege.faith
#                    liege.faith = { has_doctrine_parameter = unlock_jizya_contract } } }
# The NOR's first row can never be true when the OR's first row is false, so the
# whole expression is exactly "same faith OR the liege's faith has no jizya
# contract". Written that way below; the vanilla shape is quoted here so the next
# reader can check the simplification instead of trusting it.
#
# EVERY ROW BELOW IS INDIVIDUALLY GUARDED, and that is deliberate: a limit is an
# AND-list with no promised evaluation order, so `exists = scope:tnt_p` on one
# row cannot be relied on to protect a dotted read on another. The same-faith
# test is therefore written as `scope:tnt_p ?= { faith = root.faith }` — the
# optional-link form (R13) — rather than as `faith = scope:tnt_p.faith`.
#   faith = root.faith            GAME\common\decisions\dlc_decisions\tgp\tgp_tenet_decisions.txt:27
#   faith = { <faith trigger> }   GAME\common\character_interactions\00_alliance.txt:841
#                                 GAME\common\character_interactions\00_adoption.txt:596
# With no partner both rows read false / true respectively and the gate opens;
# the setter and the apply leg are the layers that then refuse (§0.4).
tnt_ob_revoke_ok_value = {
	# CK3 1.20.0.2 keeps Jizya's contract restriction at FAITH level:
	# GAME\common\subject_contracts\contracts\special_contracts.txt:536-566.
	# The tenet's unlock_jizya_contract is not a personal_tenet_parameter.
	# Keep these faith reads aligned with the contract we actually apply.
	# NO ROOT IN AN INTERACTION'S on_accept, so the value names the scope it stands on.
	# Full argument at tnt_52_marriage_values.txt:823-839. Guarded, because a parent
	# value or effect may already hold tnt_me and re-saving it is an error in itself.
	if = {
		limit = { NOT = { exists = scope:tnt_me } }
		if = {
			limit = { exists = scope:actor }
			scope:actor = { save_temporary_scope_as = tnt_me }
		}
		else = { save_temporary_scope_as = tnt_me }
	}
	value = 0
	if = {
		limit = { NOT = { exists = scope:tnt_p } }
		var:tnt_partner ?= { save_temporary_scope_as = tnt_p }
	}
	if = {
		limit = {
			tnt_ob_feudal_value > 0
			exists = var:tnt_vassal_p
			var:tnt_vassal_p > 0
			OR = {
				# the player is the subject, so the LIEGE is the partner
				scope:tnt_p ?= { faith = scope:tnt_me.faith }
				NOT = {
					scope:tnt_p ?= {
						faith = { has_doctrine_parameter = unlock_jizya_contract }
					}
				}
			}
		}
		add = 1
	}
	else_if = {
		limit = {
			tnt_ob_feudal_value > 0
			exists = var:tnt_vassal_r
			var:tnt_vassal_r > 0
			OR = {
				# the partner is the subject, so the LIEGE is the player (root)
				scope:tnt_p ?= { faith = scope:tnt_me.faith }
				NOT = {
					faith = { has_doctrine_parameter = unlock_jizya_contract }
				}
			}
		}
		add = 1
	}
}

#
# Each body reads as the SUBJECT's gain (+) or burden (-), then the whole thing
# is multiplied by tnt_ob_sign_value, which is -1 when the player is the subject.
#
# WHERE THE NUMBERS COME FROM — and which are vanilla and which are not.
# Vanilla prices exactly four of these, in the ai_accept of
# offer_vassalization_interaction (GAME\common\character_interactions\00_character_interactions.txt:1029-1053),
# all from the would-be vassal's point of view:
#     religious_exemption      +60   (feudal: normal tax + low levies + religious_rights)
#     religious_exemption_clan +30   (religious_rights only)
#     low_obligations          +30   (tax 1 AND levies 1, jointly)
#     high_obligations         -40   (tax 3 AND levies 3, jointly)
#     normal_obligations         0   (no modifier at all)
# and council_rights is priced +30 in the scheme-bribe menu
# (00_scheme_scripted_modifiers.txt:688-708).
#
# EVERYTHING ELSE IS EXTRAPOLATED (report 41 W-6, 30-V2-DESIGN §11 item 4):
# the split of vanilla's joint tax+levy figures, the levels 0 and 4 of both
# ladders, and the five remaining rights. The extrapolation follows each level's
# own `score` and `subject_opinion`, which are the numbers vanilla itself uses to
# rank obligations:
#     feudal_government_taxes   score  2 / 1 / 0 / -2 / -3   opinion +10/+5/0/-15/-25
#     feudal_government_levies  score  2 / 1 / 0 / -1 / -2   opinion +10/+5/0/-15/-25
#                               (GAME\common\subject_contracts\contracts\feudal.txt:1-189)
#     religious_rights          score  3      council_rights score 3
#     succession_rights         score -1
#                               (special_contracts.txt:349, :516, :454)
# Tax carries the heavier half of the joint figures because its score spread is
# wider (2..-3 against 2..-2) and because its opinion penalties bite the same.
# TUNE THESE BY PLAY, NOT BY ARGUMENT — they are the softest numbers in the
# build after the eternal hook.
#
# Every price re-tests its own §3 gate. An ungated price would bill the player
# for a line that tnt_36_hooks_contracts.txt is about to refuse to emit, which is
# the exact class of dishonesty user item 1.2 is about.
#
# 1.2.1 SCALED EXCEPTION: tax, levy, fortification and coinage prices multiply
# once by the actual subject's economic factor (1 + territorial value / 200,
# capped at 3). This is an opt-in gameplay scale, NOT a new vanilla anchor.
# The pre-signed contract convention, legality and five personal-right prices
# are unchanged. Classic multiplies by exactly 1 and retains the old figures.
#
# ===========================================================================
# v3 ITERATION 2 — WHY THIS SECTION SURVIVED THE RECALIBRATION ALMOST INTACT
# ===========================================================================
# Iteration 2 moved the whole mod off "100 points is a year of the partner's income"
# and onto raw vanilla acceptance points (tnt_50_values.txt, CALIBRATION block), and
# every other per-item price in the build shrank by roughly a factor of ten. THESE
# NINE DID NOT, because they were never on the income scale in the first place: the
# four vanilla-priced ones are lifted straight out of offer_vassalization's own
# ai_accept, which is a raw point sum like every other ai_accept in the game.
#
# THE PROOF THAT THE SPLIT IS EXACT, and it is worth writing down because it is the
# strongest evidence in the file that this section is correctly calibrated. Vanilla
# prices tax and levies JOINTLY (00_character_interactions.txt:1029-1053):
#       low_obligations   (tax 1 AND levies 1)  = +30
#       high_obligations  (tax 3 AND levies 3)  = -40
# Our split:
#       tax 1 = +20   levies 1 = +10   ->  +30   EXACT
#       tax 3 = -25   levies 3 = -15   ->  -40   EXACT
# religious_exemption +60 feudal / +30 clan and council_rights +30 are likewise
# vanilla verbatim. So six of the nine sum to vanilla's own figures to the point,
# and they are LEFT ALONE.
#
# THE ONLY EDITS: tnt_val_ob_revoke_value and tnt_val_ob_war_value moved 25 -> 20,
# to snap the two remaining invented numbers onto vanilla's offset ladder
# (00_ai_values.txt:22-34: very_low 10 / low 20 / medium 35). fortification 20,
# coinage 20 and succession -20 were already on it.
# DO NOT "rescale this section for consistency" with the rest of the build. It is
# already consistent; rescaling it is how it would stop being so.
###############################################################################

# --- 5.1 THE TWO LEVELS AS THE SHEET MUST PRINT THEM ------------------------
# UNSET MEANS NORMAL, i.e. 2 — and that is the whole reason these two values
# exist. Everywhere in script the distinction is free: tnt_val_ob_tax_value
# prices neither an absent variable nor an explicit 2, and
# tnt_exec_obligations_effect writes level 2 for both. THE GUI CANNOT DO THAT.
# TntNum reads an unset variable as 0, so a level label bound straight to
# var:tnt_ob_tax would proudly announce "Tax Exempt" on a sheet nobody has
# touched — a 45-point term the player never chose.
#
# The alternatives were worse. Initialising the variables to 2 when the window
# opens means two variables that tnt_close_window_effect has to remember to
# delete, on top of the nine the reset already handles, and a "Clear all" that

# set needs the mods-only "is this variable set" datafunction, which this mod
# deliberately never uses (gui\tnt_diplomacy_window.gui:76-79). A two-line script
# value costs nothing and cannot leak into a save.

# --- 5.2 THE SHEET FOOTER AND THE CONTRACT CARD -----------------------------

# The sheet's own footer figure and the centre column's contract card.
#
# *** DISPLAY ONLY. NEVER ADD THIS TO tnt_balance_value OR TO
# *** tnt_gain_total_value / tnt_loss_total_value. ***
# The nine prices of §4 go in individually, each with its own desc row, which is
# what makes the breakdown readable. Adding this as well double-counts the whole
# contract. Its name deliberately does NOT start with tnt_val_, the mod's prefix
# for a priced deal item, so a grep for the balance's inputs never finds it.
# V4: SCALED, BECAUSE THE HEADLINE SCALES IT. All nine obligation prices are members
# of tnt_gain_total_value, and the V4 model multiplies that total by the modifier stack
# (tnt_deal_mult_value). A panel footer quoting the raw sum was therefore quoting a
# different currency from the scales - the same defect the marriage preview had, where
# "+50 and +40" turned into +110.
#
# THE TWO LEVEL READOUTS ABOVE ARE NOT TOUCHED, and that distinction matters:
# tnt_ob_tax_shown_value and tnt_ob_levy_shown_value are OBLIGATION LEVELS (2 is the
# ordinary rate), not points. Multiplying a level by a treaty modifier would be
# nonsense - it is the price of the change that scales, not the tax band itself.
# V7 SPLIT — THE FOOTER PRINTED 0 FOREVER AT A HOSTILE TABLE, AND THE BUG WAS
# THE MULTIPLY ON A SIGNED SUM. tnt_deal_mult_value is max(0,100+S)/100, and at
# the user's test table (opinion -100 plus faith/threshold rows) S <= -100, so
# the old `multiply` zeroed WHATEVER the nine terms summed to - while the
# headline visibly moved, because there the nine prices enter RAW (their desc
# rows carry no multiply; the multiplier only scales the POSITIVE gift stack
# through tnt_gain_scale_unit_value, floored at 0). Footer said 0, scales moved:
# the user's report verbatim.
#
# THE FIX REPRODUCES THE HEADLINE'S MARGINAL ARITHMETIC IN BOTH REGIMES:
#   * a POSITIVE sheet (rights gifted to the subject) scales by the same
#     multiplier the headline applies to gifts - including honestly reading 0 at
#     mult = 0, where the headline's own marginal is 0 too;
#   * a NEGATIVE sheet (rights extracted) passes RAW, exactly as those rows
#     enter tnt_ai_accept_value.
# The footer agrees with the nine visible tnt_bd_ob_* rows in SIGN and direction
# in every regime, and with their exact sum whenever no multiplier applies (any
# all-negative sheet; any sheet at mult = 1). A MIXED-SIGN sheet is approximated
# at sum level: the multiplier is applied to the positive TOTAL here, while the
# rows display their raw per-term figures - the bounded, accepted imprecision.
tnt_ob_sheet_raw_value = {

	add = tnt_val_ob_tax_value
	add = tnt_val_ob_levy_value
	add = tnt_val_ob_relig_value
	add = tnt_val_ob_council_value
	add = tnt_val_ob_revoke_value
	add = tnt_val_ob_war_value
	add = tnt_val_ob_fort_value
	add = tnt_val_ob_coin_value
