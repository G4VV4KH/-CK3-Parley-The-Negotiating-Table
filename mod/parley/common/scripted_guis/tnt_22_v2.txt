# WHY 10 / 100 AND NOT 50 / 500

# 10 on click and 100 on right-click, which is also the standing project law R12.

# THE CAP — one clamp per entry since USER ITEM 4 (was two)
#
# The SANITY literals — gold 5000, prestige 10000, piety 10000 — are REMOVED
# mod-wide by user item 4: no magic ceiling on a deal amount. What remains is the
# AFFORDABILITY cap, the giver's actual stock — "derived from what the giver
# actually has, not a magic literal", and now the ONLY limit. Prestige and piety
# go NEGATIVE silently when overspent (41-…md §2.1: "If the giver has less than
# the amount, add_prestige with a negative value drives him negative"), so the
# stepper must not let the player compose an unpayable offer in the first place.
# tnt_send_offer.is_valid is the second line of defence, because the stock can
# fall between composing the offer and pressing Propose.
#
# INFLUENCE ALONE KEEPS ITS 1000 LITERAL (41-…md §2.8 table). The user's item 4
# named gold's 5000 and prestige/piety's 10000 and did not name influence; its
# pools are an order of magnitude smaller (monumental_influence_value is 250) and
# the government gate makes it the strictest row already, so 1000 stays.
#
# The clamp uses the contract's confirmed inline form
#     set_variable = { name = X  value = { value = var:X  min = 0  max = <cap> } }
# and the vocabulary value/add/min/max is confirmed at
# GAME\common\scripted_effects\00_diarchy_scripted_effects.txt:1002-1011.
#
# PROOF for the fields and for the cap syntax — real call sites only (Law R2, R3):
#   `prestige`  as a character script-value field:
#        GAME\common\character_interactions\00_artifact_interactions.txt:3933 (prestige > major_prestige_value)
#        GAME\common\character_interactions\00_diarch_interactions.txt:3137   (prestige < 0)
#   `piety`     GAME\common\character_interactions\00_artifact_interactions.txt:3934
#               GAME\common\character_interactions\00_alliance.txt:36 (piety >= 50)
#   `influence` GAME\common\character_interactions\10_tgp_interactions.txt:4154 (influence >= 0)
#               GAME\common\character_interactions\10_tgp_interactions.txt:4707
#               GAME\common\character_interactions\06_ep3_interactions.txt:1657
#   `max = <field>` on root:            GAME\common\script_values\03_dlc_fp2_script_values.txt:235 (max = gold)
#                                       GAME\common\script_values\07_ep3_values.txt:4938          (max = gold)
#   `max = scope:x.<field>`:            GAME\events\relations_events\friendship_events.txt:1398   (max = scope:friend.gold)
#                                       GAME\events\story_cycles\story_cycle_conqueror_events.txt:564
#   `save_temporary_scope_as` off a var inside an effect, optional-link form:
#                                       GAME\common\decisions\80_major_decisions.txt:2304
#                                       (already shipped in this mod at tnt_20_scripted_guis.txt:933)
#
# NOT USED, deliberately: `min` nested inside a `max = { }` block. A scan of every
# .txt under GAME\common found ZERO vanilla sites, so the negative-stock case is
# handled by an if/else ladder instead (see the `>= 1` limits below), never by
# nesting. A negative-prestige giver therefore lands on the else branch and the
# offered amount is forced to 0 rather than to a negative max.
#
# THE TEMPORARY SCOPE NAME IS `tnt_cap_giver`, NOT `tnt_p`.
# Defect D4 (50-RUNTIME-LOG-FINDINGS.md §D4) was exactly a temporary scope colliding
# with a permanent one of the same name. `tnt_p` is the temporary name used by all
# ~60 script-value prologues, and the permanent deal scope is now tnt_deal_partner
# (see tnt_20_scripted_guis.txt). Never introduce a third user of either name.
#
# CLEANUP OBLIGATION (30-V2-DESIGN §3.5 R-CLEAN, "for every write, name the removal")
# The eight variables written by this file are:
#   tnt_prestige_p  tnt_prestige_r  tnt_piety_p  tnt_piety_r
#   tnt_influence_p tnt_influence_r        -> must be removed by tnt_reset_offer_effect
#   tnt_infl_ok_p   tnt_infl_ok_r          -> must be removed by tnt_close_window_effect
# Both effects live in tnt_30_effects.txt, which belongs to the effects author; the
# request is recorded in NOTES2-sgui.md. Nothing here writes a variable onto any
# object that is not a character (R-CLEAN-2).
#
# v3 ITERATION 3 ADDS EXACTLY ONE MORE VARIABLE, and it is the only new save entry
# in this whole iteration:
#   tnt_ab_state    the auto-balance outcome, 1/2/3, written by group V5 and read by
#                   the button's tooltip. It is REMOVED by every one of the 48
#                   entries in groups V3 and V4 (any change to an amount voids the
#                   verdict) and by tnt_autobalance_effect itself before it runs.
#                   -> the effects author must also remove it in
#                      tnt_reset_offer_effect AND tnt_close_window_effect, so that
#                      "Clear all", closing the window and applying a deal all wipe
#                      it. Requested in the handoff.
#                   -> the 24 steppers in groups V1a-V1c above and the 8 gold
#                      steppers in tnt_20_scripted_guis.txt do NOT clear it.

#   block "tnt_stepper_plus_big"  onrightclick = "[TntExec('tnt_prestige_p_add_big')]"
#   block "tnt_stepper_text"      text         = "[TntNum('tnt_prestige_p')|0]"
# button_ignore = none is already on both button_round widgets of that type; without
# it onrightclick never fires (R12).
######################################################################################

tnt_prestige_p_add = {
	scope = character

	is_valid = {
		custom_tooltip = {
			text = tnt_err_currency_opposite_selected
			tnt_currency_p_unlocked_trigger = { CURRENCY = prestige }
		}
		custom_tooltip = {
			text = tnt_err_prestige_trade_rule
			tnt_show_prestige_p_trigger = { OTHER = var:tnt_partner }
		}
	}

	effect = {
		if = {
			limit = { tnt_currency_p_unlocked_trigger = { CURRENCY = prestige } }
			if = {
				limit = { tnt_show_prestige_p_trigger = { OTHER = var:tnt_partner } }
				if = {
					limit = { exists = var:tnt_prestige_p }
					change_variable = {
						name = tnt_prestige_p
						add = 10
					}
				}
				else = {
					set_variable = {
						name = tnt_prestige_p
						value = 10
					}
				}
				# Affordability: root is the player, and the player is the giver on the _p side.
				if = {
					limit = { prestige >= 1 }
					set_variable = {
						name = tnt_prestige_p
						value = {
							value = var:tnt_prestige_p
							min = 0
							max = prestige
						}
					}
				}
				else = {
					set_variable = {
						name = tnt_prestige_p
						value = 0
					}
				}

			}
		}
	}
}

# _r side: THE PARTNER is the giver, so the affordability cap is the partner's stock.
# The partner is reached through the object variable tnt_partner, which is guarded
# twice (Law R13): `exists = var:tnt_partner` in the limit, and the optional-link
# form `var:tnt_partner ?= { }` at the read itself. When there is no partner — the
# window cannot legally be open in that state, but a stale click can still land —
# the amount is forced to 0 instead of being left dangling.
tnt_prestige_r_add = {
	scope = character

	is_valid = {
		custom_tooltip = {
			text = tnt_err_currency_opposite_selected
			tnt_currency_r_unlocked_trigger = { CURRENCY = prestige }
		}
		custom_tooltip = {
			text = tnt_err_prestige_trade_rule
			tnt_show_prestige_r_trigger = { OTHER = var:tnt_partner }
		}
	}

	effect = {
		if = {
			limit = { tnt_currency_r_unlocked_trigger = { CURRENCY = prestige } }
			if = {
				limit = { tnt_show_prestige_r_trigger = { OTHER = var:tnt_partner } }
				if = {
					limit = { exists = var:tnt_prestige_r }
					change_variable = {
						name = tnt_prestige_r
						add = 10
					}
				}
				else = {
					set_variable = {
						name = tnt_prestige_r
						value = 10
					}
				}
				if = {
					limit = {
						exists = var:tnt_partner
						var:tnt_partner ?= { prestige >= 1 }
					}
					var:tnt_partner ?= {
						save_temporary_scope_as = tnt_cap_giver
					}
					set_variable = {
						name = tnt_prestige_r
						value = {
							value = var:tnt_prestige_r
							min = 0
							max = scope:tnt_cap_giver.prestige
						}
					}
				}
				else = {
					set_variable = {
						name = tnt_prestige_r
						value = 0
					}
				}

			}
		}
	}
}

# GROUP V1c — INFLUENCE STEPPERS (8)
#
# Influence is the Roads to Power (EP3) administrative currency, NOT a general
# resource (41-…md §2.3). It only exists for a government carrying the flag
# government_has_influence — administrative_government
# (GAME\common\governments\00_government_types.txt:490), celestial_government (:816),
# steppe_admin_government (:1116), meritocratic (:1235) and
# japan_administrative_government (GAME\common\governments\01_japan_government_types.txt:73).
#
# NOTE ON THE CITATION IN 30-V2-DESIGN: the design document cites the flag at
# "GAME\common\government_types\00_government_types.txt:487-490". There is NO
# common\government_types\ directory in 1.19 — the real path is
# GAME\common\governments\00_government_types.txt, and government_has_influence sits
# at :490 inside the administrative government's flags = { } block that opens at :486.
# The TRIGGER is proven by real call sites, not by the flags block:
#   GAME\common\character_interactions\10_tgp_japan_interactions.txt:492
#   GAME\common\character_interactions\06_ep3_interactions.txt:7145
#   GAME\events\factions\faction_demands.txt:1144
#
# Therefore each influence stepper refuses to raise the amount unless the GIVER's
# government actually has influence: the row can then never quietly compose a term
# that applies as a no-op. Sanity cap 1000 (41-…md §2.8) — KEPT under user item 4,
# which removed the gold/prestige/piety literals but did not name influence; see
# THE CAP box at the top of this file.
#
# BUILD-2 CORRECTION — THE AFFORDABILITY CAP IS DOTTED, `max = root.influence`.
# The bare form `max = influence` in a VALUE position has ZERO vanilla call sites
# (I re-measured: 0 hits for `(max|min|value|add|subtract) = influence` across
# GAME\common\** and GAME\events\**), which is exactly what
# tnt_53_currency_values.txt:219-220 warns about — "influence: NO bare call site
# exists, which is why every influence read below is dotted. Do not simplify it to
# a bare `influence`." The dotted read IS proven:
#   GAME\common\script_values\07_ep3_values.txt:5552-5553
#     value = scope:heretic.influence   subtract = root.influence
# root is the player here, so the two forms mean the same thing and only the
# proven one ships. The `influence >= 1` row in the LIMIT stays bare: that is a
# trigger, and the bare trigger form is proven at
# GAME\common\character_interactions\10_tgp_interactions.txt:4154 (`influence >= 0`).
#
# For the effects author: the transfer effect is `change_influence` with a negative
# value — `add_influence` and `remove_influence` DO NOT EXIST and are blacklisted
# (41-…md §2.2/§2.9, project law R4). Vanilla's two-call pattern is at
# GAME\common\character_interactions\00_invite_agent_to_scheme.txt:168-176.

# GROUP V2 — THE MIRROR WRITER (1)
#
# THE PROBLEM. `government_has_flag` is a SCRIPT trigger. The GUI cannot call it on a
# scope it reaches through one of our variables, so the two influence rows cannot gate
# their own visibility. (For the PLAYER alone the GUI does have a proven datafunction —
# GetPlayer.GetGovernment.HasGovernmentFlag( 'government_has_influence' ),
# GAME\gui\hud.gui:6732, GAME\gui\window_character.gui:5421, GAME\gui\window_ledger.gui:6273 —
# but for the PARTNER it would need the unproven chain
# TntVar('tnt_partner').Char.GetGovernment.HasGovernmentFlag(...). Rather than ship
# one proven read and one guess, both sides go through the same mirror.)
#
# THE ANSWER. Two ordinary 0/1 player variables, written once per window open:
#   tnt_infl_ok_p = 1  <=>  the PLAYER's government has influence
#   tnt_infl_ok_r = 1  <=>  the PARTNER's government has influence
# Absent means "no", exactly like every other toggle in this mod, so the GUI reads
#   visible = "[TntOn('tnt_infl_ok_p')]"
# which is one map lookup per frame and calls no scripted_gui at all (Law R11).
#
# WHERE IT IS CALLED FROM — BUILD 2 COLLAPSED THIS TO ONE COPY.
# The first build shipped the government test TWICE: once here and once as the
# identical scripted EFFECT tnt_refresh_v2_mirrors_effect in tnt_30_effects.txt, with
# each file instructing the other to keep the two in sync. Only the effect had a
# caller (tnt_open_window_effect:85), so this entry was the one scripted_gui in the mod
# with no caller anywhere in gui/, and the duplicate was pure drift risk.
#
# THE BODY IS NOW A ONE-LINE FORWARDER to that effect, which is exactly the collapse

# GROUP V3 — THE COARSE STEP TIER (16)   user ADD-2, v3 iteration 3
#
#=====================================================================================
# FIRST, THE ANSWER TO THE QUESTION THE BUILD ORDER ASKED: A CK3 BUTTON HAS NO
# MODIFIER-CLICK HANDLER. THERE IS NO THIRD CLICK TO BIND ±1000 TO.
#=====================================================================================
# Measured over EVERY .gui AND EVERY .txt under
# <game>:
#     onshiftclick      0 hits        oncontrolclick   0 hits
#     onaltclick        0 hits        onctrlclick      0 hits
#     onmiddleclick     0 hits        shiftclick       0 hits
#     onmouseclick      0 hits        on_shift_click   0 hits
#     onclick         (thousands)     onrightclick    86 hits, e.g.
#                                       GAME\gui\shared\coat_of_arms.gui
#                                       GAME\gui\event_windows\duel_event.gui
#                                       GAME\gui\activity_window_widgets\funeral_deceased_selection.gui
# A CK3 widget therefore exposes exactly TWO click handlers, and this mod already
# spends both: onclick = ±10, onrightclick = ±100.
#
# SO THE COARSE TIER IS ITS OWN PAIR OF BUTTONS. *** GUI AUTHOR: BUILD SHAPE B. ***
# Each currency row needs two more small buttons — a "«" and a "»", or a doubled
# chevron — bound to the entries below with plain onclick:
#     onclick = "[TntExec('tnt_gold_p_sub_huge')]"
#     onclick = "[TntExec('tnt_gold_p_add_huge')]"
# They need NO button_ignore = none: that attribute exists only so that
# onrightclick fires (see the note at the top of this file), and nothing here uses
# the right button.
#
#=====================================================================================
# THE STEPS, AND WHY INFLUENCE IS 250 AND NOT 1000
#=====================================================================================
#   gold      ±1000   prestige ±1000   piety ±1000   influence ±250
# Since user item 4 the first three rows have NO literal ceiling — the giver's
# stock is the range — so "full range in N clicks" is now a fact about the purse,
# not about a cap. Influence pools are an order of magnitude smaller than the
# other three — monumental_influence_value is 250 against monumental_prestige_value
# 1500 — so ±1000 on a row still capped at 1000 (the one surviving literal, see
# THE CAP box) would not be a coarse step, it would be a jump straight to the
# ceiling, which the `_max` preset below already provides in one click and labels
# honestly. 250 IS vanilla's own top influence band
# (GAME\common\script_values\07_ep3_values.txt:7, monumental_influence_value).
#
#=====================================================================================
# WHERE THE CLAMPING LIVES NOW
#=====================================================================================
# Not here. Every entry in groups V3 and V4 is a forwarder into one of the
# amount helpers in common\scripted_effects\tnt_39_autobalance.txt, so the
# clamp — the giver's actual stock (user item 4 deleted the sanity-cap half and
# the CAP parameter with it) — is written ONCE per shape instead of 48 times.
# That file's header carries the vanilla proof for the textual parameter
# substitution this depends on (`name = $VAR$`, `var:$VAR$`, `max = $FIELD$`)
# and for the clamp shape itself. The 24 entries in groups V1a-V1c
# above are left exactly as they shipped — they work, and rewriting a running
# stepper to save lines is not a trade this file makes.
#
# GOLD NOW CLAMPS TO THE STOCK LIKE EVERY OTHER ROW (user item 14). This block used
# to say the opposite — that gold was the one row without an affordability clamp, on
# purpose, because the 8 fine gold steppers in tnt_20_scripted_guis.txt group A had
# none either. Both halves of that arrangement are gone:
#   * those 8 fine steppers now carry the same `>= 1` ladder the prestige steppers
#     carry (tnt_20_scripted_guis.txt group A);
#   * the 4 coarse gold entries below no longer call tnt_cur_step_effect. They call
#     tnt_cur_step_p_effect / tnt_cur_step_r_effect with FIELD = gold, exactly like
#     their prestige and piety siblings, which also buys them the
#     `remove_variable = tnt_ab_state` those helpers end with.
# `gold` is legal bare in a value position: GAME\common\script_values\
# 03_dlc_fp2_script_values.txt:235 and 07_ep3_values.txt:4938. The ladder is what
# handles gold going negative — below 1 gold the amount is forced to 0, never to a
# negative max. tnt_gold_shortfall_value in tnt_send_offer.is_valid remains the
# SECOND line of defence, because stock can fall between composing and proposing.
# Every PRESET in group V4 already clamped to the stock, gold included.
#
# tnt_cur_step_effect (the old sanity-clamp-only helper A1) had ZERO callers after
# this change and is now DELETED outright: user item 4 removed the sanity caps, so
# a helper whose only job was that clamp had no honest reason to stay defined.
######################################################################################

# THIS IS THE HALF THAT ACTUALLY REMOVES THE CLICKING. A coarse step still needs
# five clicks to move 5000 gold; a preset needs one, and it needs one regardless of
# how big the number is, because it is a STATEMENT rather than an amount.
#
# FOUR PER CURRENCY PER SIDE, and the GUI author binds all four with plain onclick:
#   _std    "a year of my income"     — for GOLD that is literally
#                                       yearly_character_income (the partner's own
#                                       income on the _r side). For prestige, piety
#                                       and influence CK3 exposes NO income field at
#                                       all, so the preset pays one full vanilla
#                                       bribe instead — 300 prestige / 250 piety /
#                                       250 influence between two dukes, which is
#                                       worth exactly +20 on the deal sheet. The
#                                       derivation is written out in
#                                       tnt_53_currency_values.txt §5; the label for
#                                       these three must say "a customary gift", not
#                                       "a year", or the button lies.
#   _half   "half of what I hold"     — the giver's stock x 0.5
#   _max    "everything I can afford" — the giver's stock, whole (influence alone
#                                       still crops at its surviving 1000 literal)
#   _none   "nothing"                 — remove_variable, i.e. exactly the state
#                                       tnt_reset_offer_effect leaves this row in
#

# A ruler with 40 gold and an income of 300 who presses "a year of my income"
# offers 40. A ruler in debt offers 0 and cannot be talked into a negative row.
#
# NOTHING HERE INVENTS A NUMBER. The only literals are influence's surviving 1000
# cap (user item 4 deleted the other three sanity caps and the CAP parameter) and
# the two fractions 0.5 and 1. Every amount is read off a real field or a named value.

# GROUP V5 - AUTO-BALANCE
# Section C of tnt_39_autobalance.txt searches the actual rounded acceptance.
# Target +1; if currency granularity prevents it, retain the smallest payable
# acceptable result and show state 4. State 2 means no table change.
# Keep the button available at +1 as well: older saves may contain offsetting
# payments at that score, and normalization must remain reachable.
tnt_autobalance = {
	scope = character

	# THE BUTTON WORKS IN BOTH DIRECTIONS NOW, AND V4 IS WHAT BROKE THE OTHER ONE.
	# The old row was `tnt_ai_accept_value < 1`, i.e. the button was VALID ONLY WHILE
	# THE DEAL WAS BAD FOR THE PARTNER. That is exactly backwards for the user's
	# request: "если увести очки далеко в плюс и нажать 'уравновесить' - добавятся
	# опции чтобы довести до максимального приблежения к +1". Pushing the treaty to
	# +80 and pressing the button did nothing at all, because the gate refused before
	# the effect ever ran - and the effect itself has always had a surplus branch.
	#
	# The predicate is "the deal is not already exactly +1", written as an OR of two
	# named-value-against-literal comparisons because that is the only comparison
	# form Law R7 permits (a named value against a variable is forbidden).
	is_valid = {
		# This row is both the readable reason and the cheap fail-closed boundary.
		# Everything which evaluates tnt_ai_accept_value sits inside the guarded
		# trigger_if below, so a closed or invalidated table cannot flood the log.
		custom_description = {
			text = tnt_err_no_partner
			exists = var:tnt_open
			exists = var:tnt_partner
		}
		trigger_if = {
			limit = {
				exists = var:tnt_open
				exists = var:tnt_partner
			}
		custom_description = {
			text = tnt_err_ab_empty
			# A selected threat is a real priced term, but deliberately is not part
			# of tnt_items_count_value: threat-only must never become sendable and
			# farm dread/opinion. It may, however, seed Equalize so the effect can
			# add genuine consideration on the partner's side.
			OR = {
				tnt_offer_nonempty_trigger = yes
				AND = {
					exists = var:tnt_threat_p
					var:tnt_threat_p > 0
					tnt_val_threat_p_value > 0
				}
			}
		}

		#==============================================================================
		# TWO INFORMATIONAL ROWS — ITEM 5's SECOND HALF. THEY MUST BE UNCONDITIONALLY
		# TRUE, AND THAT IS NOT A STYLE POINT.
		#
		# is_valid IS the tooltip: the GUI binds `enabled = [TntValid(...)]` next to
		# `tooltip = [TntTip(...)]` (tnt_types.gui), so every row in here is printed —
		# and every row in here that reads FALSE also GREYS THE BUTTON OUT. A hint
		# written as an ordinary custom_description with a real condition would
		# therefore disable the button on precisely the treaties it is meant to
		# describe. `always = yes` is the only honest way to say something in a
		# validity block.
		#
		# THE HINT IS ALWAYS SHOWN because it describes what the button does, which is
		# true before the first press. THE LINE is wrapped in a trigger_if instead:
		# when the limit is false the whole trigger_if is TRUE and prints nothing, so
		# the row appears only after a press that actually took something, and the
		# button's enabled state is untouched either way. tnt_ab_lumpy_n is removed
		# again by tnt_autobalance_effect when a press took nothing, so `exists` alone
		# would nearly do — the `> 0` is the belt to that braces.
		#
		# Both are variable-against-literal tests (Law R7) and neither costs a script
		# value evaluation on a per-frame binding (Law R9).
		#
		# BOTH SHAPES ARE VANILLA, VERBATIM:
		#   custom_description = { text = X  always = yes }
		#     GAME\common\character_interactions\10_tgp_interactions.txt:11246-11249
		#   trigger_if = { limit = { … }  custom_description = { … } }
		#     GAME\common\character_interactions\00_alliance.txt:3257
		#     GAME\common\character_interactions\00_artifact_interactions.txt:4071
		#     GAME\common\character_interactions\00_diarch_interactions.txt:116
		#==============================================================================
		custom_description = {
			text = tnt_ab_lumpy_hint
			always = yes
		}
		trigger_if = {
			limit = {
				exists = var:tnt_ab_lumpy_n
				var:tnt_ab_lumpy_n > 0
			}
			custom_description = {
				text = tnt_ab_lumpy_line
				always = yes
			}
		}
		}
	}

	effect = {
		if = {
			limit = {
				exists = var:tnt_open
				exists = var:tnt_partner
			}
			tnt_autobalance_effect = {
				MARGIN = 1
				CEILING = 1
			}
		}
	}
}
