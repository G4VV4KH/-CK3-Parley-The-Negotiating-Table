#
# ASCII ONLY IN THIS FILE, DELIBERATELY, exactly as in tnt_37_ai_offer.txt, so no
# tool in the chain can turn a dash or a section sign into mojibake. The rule has
# ONE standing exception and no others: the two places where the user's own Russian

#=======================================================================
# WHY THE AMOUNT HELPERS LIVE IN A scripted_effects FILE AND NOT IN THE
# scripted_guis FILE
#=======================================================================
# ADD-2 needs 16 coarse steppers and 32 presets. Written out longhand in
# tnt_22_v2.txt that is ~1500 lines of near-identical clamping, i.e. 48 places
# where one clamp can rot out of step with the other 47 - and the clamps are the
# load-bearing part, because prestige, piety and influence all go NEGATIVE
# SILENTLY when overspent (tnt_53_currency_values.txt section 0.4).
#
# So the clamp is written ONCE per shape here and every scripted_gui is a
# forwarder of four lines. That works because a scripted effect substitutes its
# parameters TEXTUALLY, including into a variable NAME and into a field position,
# and all four forms are proven in vanilla:
#   name = $VARIABLE$          GAME\common\scripted_effects\00_achievement_effects.txt:22
#                              GAME\common\scripted_effects\00_diarchy_scripted_effects.txt:44
#                              GAME\common\scripted_effects\00_debug_and_shortcut_effects.txt:12
#   var:$VAR$ / exists         GAME\common\scripted_effects\00_debug_and_shortcut_effects.txt:9
#                              GAME\common\scripted_effects\00_scripted_effects.txt:15
#   min = $MIN$ / multiply = $MULT$
#                              GAME\common\scripted_effects\04_dlc_ep2_tour_effects.txt:359
#                              GAME\common\scripted_effects\00_diarchy_scripted_effects.txt:1432
#   a dotted field chain as a parameter
#                              GAME\common\scripted_effects\06_dlc_ce1_legitimacy_effects.txt:415
#
# THE CLAMP SHAPE ITSELF is the one already shipped by the 24 currency steppers:
#   set_variable = { name = X  value = { value = var:X  <op>  min = 0  max = <cap> } }
# and its vanilla proof is verbatim at
#   GAME\common\scripted_effects\00_diarchy_scripted_effects.txt:1002-1011
# which is the same `set_variable / value = { value = var:X  add = { value = <named
# value>  multiply = <named value> } }` this file uses in the sweeten pass.
#
# ONE CLAMP PER WRITE SINCE USER ITEM 4 (was two): the AFFORDABILITY cap, the
# giver's actual stock, applied through the if/else ladder and NEVER through a
# `min` nested inside a `max = { }` block, which has zero vanilla call sites.
# A negative-stock giver lands on the else branch and the amount is forced to 0.
# The old SANITY caps - gold 5000, prestige 10000, piety 10000 - are DELETED
# mod-wide together with the $CAP$ parameter that carried them: the user's item 4
# ruling is that what the giver holds is the only ceiling a deal amount has.
# INFLUENCE ALONE KEEPS ITS 1000 LITERAL, written out in section B: the ruling
# named the other three literals and not this one, and influence is the smallest
# and strictest row already (government gate, 250-sized vanilla pools).
#
# tnt_cur_step_effect (the old A1, sanity clamp ONLY, zero callers since user
# item 14 moved the coarse gold steppers onto A2/A3) is DELETED: with the sanity
# cap itself removed, a helper whose only job was that clamp was not a record any
# more, it was a trap. Any new currency stepper wants A2 or A3.
#
# Every PRESET, gold included, always did clamp to the stock, because a preset is a
# statement about what the giver holds and "everything I can afford" is
# meaningless without it.
#
# EVERY HELPER ENDS WITH `remove_variable = tnt_ab_state`, so any click that
# changes an amount voids the auto-balance verdict its tooltip would otherwise
# still be showing. See section C for what that variable is.
########################################################################

# SECTION A - THE GENERIC AMOUNT HELPERS  (gold, prestige, piety)
#
# root is ALWAYS the player. `_p` = the PLAYER gives it, `_r` = the PARTNER gives
# it (contract R0.1), so the affordability field is read off root in the `_p`
# helpers and off var:tnt_partner in the `_r` helpers.
#
# FIELD is a bare character field - `gold`, `prestige`, `piety`. All three are
# proven bare in a trigger AND in a value position:
#   max = gold        GAME\common\script_values\03_dlc_fp2_script_values.txt:235
#   max = prestige    shipped, tnt_22_v2.txt (the 8 prestige steppers)
#   piety >= 50       GAME\common\character_interactions\00_alliance.txt:36
# INFLUENCE IS NOT ONE OF THEM and must never be passed as FIELD here: it has no
# bare call site in a value position at all (tnt_53_currency_values.txt:249-250)
# and it needs the government gate. Influence has its own six helpers, section B.
#
# The partner-side helpers read the partner twice, both times guarded (Law R13):
# `exists = var:tnt_partner` plus the optional-link form `var:tnt_partner ?= { }`,
# and the temporary scope is named tnt_cap_giver - never tnt_p, which is the
# temporary name the ~60 script-value prologues use, and never tnt_deal_partner,
# which is permanent (defect D4).
########################################################################

# (A1, tnt_cur_step_effect, stood here: sanity clamp only, zero callers. Deleted
# with the sanity caps under user item 4 - see the header.)
# `add = <negative literal>` is proven: GAME\common\scripted_modifiers\00_scheme_scripted_modifiers.txt:711
# (`add = -1` inside a value block).

# A2 - STEP BY A SIGNED DELTA, THE PLAYER IS THE GIVER.
tnt_cur_step_p_effect = {
	if = {
		limit = { NOT = { exists = var:$VAR$ } }
		set_variable = {
			name = $VAR$
			value = 0
		}
	}
	set_variable = {
		name = $VAR$
		value = {
			value = var:$VAR$
			add = $DELTA$
			min = 0
		}
	}
	if = {
		limit = { $FIELD$ >= 1 }
		set_variable = {
			name = $VAR$
			value = {
				value = var:$VAR$
				min = 0
				max = $FIELD$
			}
		}
	}
	else = {
		set_variable = {
			name = $VAR$
			value = 0
		}
	}
	remove_variable = tnt_ab_state
}

# A6 - SET A FRACTION OF WHAT THE PLAYER HOLDS.
# MULT = 0.5 is "half of what I hold"; MULT = 1 is "everything I can afford".
# No if/else ladder is needed here and none is used: the amount IS the stock, so
# `min = 0` alone already forces a negative-stock giver to 0, and since user
# item 4 there is no other ceiling. That is why "everything I can afford" is
# expressed as MULT = 1 rather than as a named per-currency value - there is
# nothing left to name.
tnt_cur_frac_p_effect = {
	set_variable = {
		name = $VAR$
		value = {
			value = $FIELD$
			multiply = $MULT$
			min = 0
			round = yes
		}
	}
	remove_variable = tnt_ab_state
}

# A8 - CLEAR THIS CURRENCY. "Nothing", the fourth preset.
# remove_variable and not `value = 0`, so that BOTH `exists = var:X` and
# `var:X > 0` read false afterwards - the exact state tnt_reset_offer_effect
# leaves, and therefore the one state every valuation, every shortfall and every
# GUI binding in the mod already handles. An unguarded remove_variable on an
# absent variable is silent (GAME\common\scripted_effects\00_scripted_effects.txt:61-62).
tnt_cur_clear_effect = {
	remove_variable = $VAR$
	remove_variable = tnt_ab_state
}

# SECTION B - THE SIX INFLUENCE HELPERS
#
# Influence is the Roads to Power administrative currency and needs two things
# the generic helpers cannot express:
#   1. THE GOVERNMENT GATE. `change_influence` on a character whose government
#      holds no influence pool is a silent no-op, so a row composed without the
#      gate looks paid for and does nothing. The flag is government_has_influence
#      (GAME\common\governments\00_government_types.txt:490); the trigger's proof
#      is real call sites, not the flags block:
#        GAME\common\character_interactions\06_ep3_interactions.txt:7145
#        GAME\common\character_interactions\10_tgp_japan_interactions.txt:492
#   2. A DOTTED READ IN EVERY VALUE POSITION. `max = influence` bare has ZERO
#      vanilla call sites; the dotted form is proven at
#      GAME\common\script_values\07_ep3_values.txt:5552-5553. The bare form stays
#      in the LIMIT, where it is a trigger and is proven at
#      GAME\common\character_interactions\10_tgp_interactions.txt:4154.
# The variable name and the 1000 sanity cap are the same in every call, so they
# are written out rather than parameterised. The 1000 literal SURVIVES user
# item 4, which removed the gold/prestige/piety caps but did not name influence
# (argued in full at the top of tnt_22_v2.txt, THE CAP box).
########################################################################

tnt_infl_p_step_effect = {
	if = {
		limit = { NOT = { exists = var:tnt_influence_p } }
		set_variable = {
			name = tnt_influence_p
			value = 0
		}
	}
	set_variable = {
		name = tnt_influence_p
		value = {
			value = var:tnt_influence_p
			add = $DELTA$
			min = 0
			max = 1000
		}
	}
	if = {
		limit = {
			government_has_flag = government_has_influence
			influence >= 1
		}
		set_variable = {
			name = tnt_influence_p
			value = {
				value = var:tnt_influence_p
				min = 0
				max = root.influence
			}
		}
	}
	else = {
		set_variable = {
			name = tnt_influence_p
			value = 0
		}
	}
	remove_variable = tnt_ab_state
}

# SECTION C - CURRENCY BALANCING
# Both the window and incoming AI letters use the actual acceptance value.
# This includes personality, relationship scaling, signed obligations and all
# three rounding stages. Nominal currency prices are not an inverse of it.
# Discard forbidden directions before pricing or netting; remove overpayment
# before requesting a new payment. Never create
# two directions of the same currency. A rounded +2 can be the minimum: do not
# manufacture a counterpayment merely to make that number look like +1.
# World AI-to-AI trades use their separate dispatcher, not these effects.
########################################################################

# Move one amount toward BOUND. Increasing acceptance finds the SMALLEST
# movement reaching the target. Decreasing acceptance finds the LARGEST
# movement that still meets it. Endpoint probes handle exhausted wallets.
# Probe exact endpoints, including fractional wallets; integer-sized moves halve
# the interval to <=1 unit. Preserve the accepting bound. 32 is a hard ceiling.
# floor is native (00_council_values.txt); parameterized variable names already
# occur in the amount helpers above. Every search variable is removed on exit.
tnt_ab_search_effect = {
	set_variable = { name = tnt_ab_search_base value = var:$VAR$ }
	set_variable = { name = tnt_ab_search_direction value = $DIRECTION$ }
	set_variable = { name = tnt_ab_search_lo value = 0 }
	set_variable = {
		name = tnt_ab_search_hi
		value = { value = $BOUND$ subtract = var:tnt_ab_search_base multiply = $STEP$ min = 0 }
	}
	if = {
		limit = { var:tnt_ab_search_hi > 0 }
		set_variable = {
			name = $VAR$
			value = { value = var:tnt_ab_search_hi multiply = $STEP$ add = var:tnt_ab_search_base }
		}
		if = {
			limit = {
				OR = {
					AND = { var:tnt_ab_search_direction > 0 tnt_ab_search_gap_value <= 0 }
					AND = { var:tnt_ab_search_direction < 0 tnt_ab_search_gap_value > 0 }
				}
			}
			while = {
				count = 32
				limit = { tnt_ab_search_span_value > 1 }
				set_variable = {
					name = tnt_ab_search_mid
					value = { value = var:tnt_ab_search_lo add = var:tnt_ab_search_hi divide = 2 floor = yes }
				}
				set_variable = {
					name = $VAR$
					value = { value = var:tnt_ab_search_mid multiply = $STEP$ add = var:tnt_ab_search_base }
				}
				if = {
					limit = {
						OR = {
							AND = { var:tnt_ab_search_direction > 0 tnt_ab_search_gap_value <= 0 }
							AND = { var:tnt_ab_search_direction < 0 tnt_ab_search_gap_value > 0 }
						}
					}
					set_variable = { name = tnt_ab_search_hi value = var:tnt_ab_search_mid }
				}
				else = { set_variable = { name = tnt_ab_search_lo value = var:tnt_ab_search_mid } }
			}
			if = {
				limit = { var:tnt_ab_search_direction > 0 }
				set_variable = {
					name = $VAR$
					value = { value = var:tnt_ab_search_hi multiply = $STEP$ add = var:tnt_ab_search_base }
				}
			}
			else = {
				set_variable = {
					name = $VAR$
					value = { value = var:tnt_ab_search_lo multiply = $STEP$ add = var:tnt_ab_search_base }
				}
			}
		}
	}
	remove_variable = tnt_ab_search_base
	remove_variable = tnt_ab_search_direction
	remove_variable = tnt_ab_search_lo
	remove_variable = tnt_ab_search_hi
	remove_variable = tnt_ab_search_mid
}

tnt_ab_reduce_return_currency_effect = {
	if = {
		limit = { tnt_ab_deficit_value > 0 exists = var:$VAR$ var:$VAR$ > 0 }
		tnt_ab_search_effect = { VAR = $VAR$ BOUND = 0 STEP = -1 DIRECTION = 1 }
	}
}

tnt_ab_add_offer_currency_effect = {
	if = {
		limit = {
			tnt_ab_deficit_value > 0
			OR = {
				NOT = { exists = var:$R$ }
				var:$R$ <= 0
			}
		}
		tnt_ab_search_effect = { VAR = $P$ BOUND = $CAP$ STEP = 1 DIRECTION = 1 }
	}
}

# Gold and influence permit both directions. Prestige and piety call these
# halves separately so the actual giver controls each currency-rule check.
tnt_ab_close_deficit_currency_effect = {
	tnt_ab_reduce_return_currency_effect = { VAR = $R$ }
	tnt_ab_add_offer_currency_effect = { P = $P$ R = $R$ CAP = $CAP$ }
}

tnt_ab_trim_currency_effect = {
	if = {
		limit = { tnt_ab_search_gap_value <= 0 var:$VAR$ > 0 }
		tnt_ab_search_effect = { VAR = $VAR$ BOUND = 0 STEP = -1 DIRECTION = -1 }
	}
}

tnt_ab_pay_currency_effect = {
	if = {
		limit = { tnt_ab_surplus_value > 0 }
		tnt_ab_search_effect = { VAR = $VAR$ BOUND = $CAP$ STEP = 1 DIRECTION = -1 }
	}
}

tnt_ab_net_effect = {
	if = {
		limit = {
			exists = var:tnt_gold_p
			var:tnt_gold_p > 0
			exists = var:tnt_gold_r
			var:tnt_gold_r > 0
		}
		set_variable = {
			name = tnt_ab_net
			value = {
				value = var:tnt_gold_p
				subtract = var:tnt_gold_r
			}
		}
		if = {
			limit = { var:tnt_ab_net > 0 }
			set_variable = {
				name = tnt_ab_net
				value = var:tnt_gold_r
			}
		}
		else = {
			set_variable = {
				name = tnt_ab_net
				value = var:tnt_gold_p
			}
		}
		set_variable = {
			name = tnt_gold_p
			value = {

# SECTION D - THE LUMPY LADDER  (user item 5, second half)
#
# WHAT THE USER ASKED FOR - his own sentence is quoted in Russian at the head of
# tnt_autobalance in tnt_22_v2.txt and in C1 above, and it says: push the points
# far into the plus, press "balance", and OPTIONS GET ADDED until the deal is as
# close to +1 as it can be. Section C's answer was "add MORE CURRENCY to his
# column" - the word he used was options, not gold. That answer also runs
# out: a partner with 12 gold and no prestige cannot pay off a 200-point surplus in
# coin, and the button then fell back on deleting the player's own gift. This
# section is the missing rung - the partner pays in LAND, in a CLAIM, or with his
# CROWN, exactly as a Total War counter-offer would.
#
#=======================================================================
# D.0  THE ONE-DIRECTION RULE, AND WHY IT IS NOT NEGOTIABLE
#=======================================================================
# EVERY term this section can add lands on the PARTNER's column - `_r`. Nothing
# here can ever write a `_p` variable or a `_p` selection list. Integration
# contract R9 rejected the mirrored "aggressive balancing" toggle outright and
# forbids re-proposing it in this pass; its one-sentence argument is the whole
# reason this section is safe to ship: a balance button whose value proposition is
# "the mod may now cede your land because you ticked a box three minutes ago" is a
# worse feature than no button at all.
#
# It follows that this section only ever runs in the SURPLUS branch. A deficit is
# closed by making the PLAYER pay, and the player pays in currency only.
#
#=======================================================================
# D.1  WHY THERE IS NO RANDOMNESS HERE, AND WHAT REPLACED IT
#=======================================================================
# The design this section implements asked for a random draw over the candidate
# list plus a re-roll button. Integration contract R2 rejected `random_in_list` and
# `random_list` for this ladder and deleted the seasoning rung with them, and the
# reason is not style:
#   the chain "scripted_gui effect -> scripted effect -> random draw" has NO
#   verbatim vanilla call site, and if GetScriptedGui.Execute is not a synced
#   command then every client in a multiplayer game draws a DIFFERENT title and the
#   session desyncs. A desync is the one failure class the implementer cannot
#   detect from script and the user cannot work around.
# So selection is a DETERMINISTIC ORDERED WALK: rebuild nothing, walk the candidate
# list the fill effects already built, skip what is vetoed, and take the FIRST
# survivor whose price fits the surplus.
#
# VARIETY ACROSS PRESSES IS THEREFORE FREE AND NEEDS NO SEED. Press one takes
# candidate A and MOVES it out of the candidate list into the selection list (the
# two-list invariant, tnt_35_multiselect.txt), so press two cannot see A at all and
# takes B. If the player then deletes A, A goes back among the candidates - but it
# also goes into the veto list, so press three still cannot take it. The behaviour
# the re-roll button was for ("show me a different one") is what deleting one and
# pressing again already does, and it is reproducible on every client.
#
#=======================================================================
# D.2  THE FIT TEST - WHY A CONSERVATIVE UPPER BOUND AND NOT THE REAL PRICE
#=======================================================================
# A lumpy term is priced by an ITERATOR over the selection list
# (tnt_val_title_multi_r_value / tnt_val_claim_multi_r_value,
# tnt_54_multiselect_values.txt), so its price is only readable AFTER it has been
# put on the table. Reading a candidate's own price before choosing it would mean
# either a script value that takes a parameter - which does not exist - or a
# tentative add followed by a rollback, and a rollback would have to ADD to the
# very list the walk is iterating, which is the one list mutation vanilla does not
# sanction (it sanctions removal during iteration, story_cycle_infidelity_
# confrontation.txt:45-64, and that is all).
#
# SO THE WALK COMPARES AGAINST AN UPPER BOUND OF THE PRICE, computed from the
# candidate's TIER, which is readable for free. Every multiplier in those two
# valuations is >= 1 and bounded, so the bound is exact arithmetic and not a guess:
#
#   CEDED TITLE (tnt_val_title_multi_r_value:454-523)
#     base by tier      15 / 30 / 45 / 60 / 75   barony..empire
#     x1.4  the land is de jure ours already
#     x1.25 its province shares our culture
#     x1.20 the two realms are neighbours   (per deal, applied to the whole sum)
#     -> worst case  base x 2.1              31.5 / 63 / 94.5 / 126 / 157.5
#
#   GRANTED CLAIM (tnt_val_claim_multi_r_value:574-611)
#     same tier base, x0.5 because a claim is a licence and not land,
#     x1.3 when the current holder is the weaker party
#     -> worst case  base x 0.65             9.75 / 19.5 / 29.25 / 39 / 48.75
#
#   FEALTY (tnt_val_vassal_r_value, tnt_50_values.txt:2175-2253)
#     100 + 5 x his realm_size, and the `add` block carries `max = 250`
#     -> worst case  250, a hard ceiling written in the value itself
#
# THE +2 ON EVERY LITERAL BELOW IS THE ROUNDING CUSHION, not padding.
# tnt_loss_total_value and tnt_ai_accept_value both end in `round = yes`, so the
# headline can move one point further than the term's own arithmetic says. Two
# points of cushion keeps a term that "just fits" from landing the headline on 0,
# which DECLINES (tnt_50_values.txt:3537-3543). The safety sweeten pass at the foot
# of the surplus branch is the second net and it was already there.
#
# *** KEEP IN STEP - THE ONE MAINTENANCE HAZARD THIS SECTION CREATES. ***
# The five title literals and the five claim literals below are DERIVED from
# tnt_val_title_multi_r_value and tnt_val_claim_multi_r_value
# (common\script_values\tnt_54_multiselect_values.txt) and from
# tnt_val_vassal_r_value (tnt_50_values.txt). Retune any of those three and these
# bounds stop being bounds - and the failure is silent and one-sided: an
# UNDER-estimate lets the ladder take a term that drives the headline below +1, and
# only the safety sweeten pass at the foot of the surplus branch catches it, by
# spending the player's gold on a purchase he did not authorise. The deferred claim
# reprice on the backlog (x0.5 -> x0.8) is exactly such a change: it would make
# every claim literal here understate the price by 60 %. Whoever lands it lands
# both files in one commit.
#
# CONSEQUENCE, AND IT IS THE DESIRED ONE: the button is CAUTIOUS. It will not
# demand a county until the treaty is about 65 points over the acceptance point -
# roughly a thousand gold of over-generosity at duke tier - and it will not demand
# a crown under 252. Anything smaller is settled in coin by the pay ladder above,
# which is where a small imbalance belongs.
#
# BECAUSE THE BOUND IS AN OVER-ESTIMATE, THE LADDER CANNOT OVERSHOOT. The realised
# price is always <= the bound <= the surplus, so the headline after a take is
# always >= the ceiling, i.e. >= +1. It converges from ABOVE, every time, which is
# precisely what lets tnt_ab_exact_land_effect stay the last statement and close
# the remainder exactly: that pass only ever moves the headline DOWN and only fires
# above +1, so a ladder that never dips below +1 hands it a problem it can always
# solve. Put a rung after the exact landing and the +1 promise is void.
#
#=======================================================================
# D.3  tnt_ab_snap - ONE VARIABLE DOING TWO JOBS ON PURPOSE
#=======================================================================
# The fit test has to be readable INSIDE the walk, where the scope is a TITLE and
# not the player, so `tnt_ab_surplus_value` - which reads var:tnt_ab_ceiling off
# the player - cannot be evaluated there at all. tnt_ab_snap is the surplus
# SNAPSHOT taken on the player before each pass, so every comparison in the walk is
# a variable against a LITERAL, read inside `scope:tnt_ab_owner = { }`. That is the
# only comparison form Law R7 permits and it is also the cheapest.
#
# ITS SECOND JOB: after a take, the pass sets it to 0. That single write ends the
# walk (no tier's bound is <= 0), skips every remaining rung of the same pass, and
# is honest - once the table has changed, the snapshot no longer describes the
# world and must not be spent twice. One take per pass, enforced by arithmetic
# rather than by a flag.
#
# It is removed at the end of every pass, so it can never reach a save.
#
#=======================================================================
# D.4  RUNG ORDER: FEALTY, THEN TITLE   (V13: the claim rung is retired)
#=======================================================================
# Biggest instrument first, each behind its own fit gate, so the size of the thing
# demanded is proportionate to the size of the debt. A surplus that can absorb a
# crown is a surplus that came from an extraordinary gift; a surplus of 70 points
# reaches only the title rung. Walking the ladder
# the other way round would answer a 300-point over-payment with the smallest
# instrument on the table and then need three more presses to finish the job.
#
# V13, USER ITEM 1: THE THIRD RUNG IS GONE. "one of 25 only the claim rung" was
# true until the granted claim was retired (TOMBSTONE C in tnt_32_apply.txt); a
# surplus that small is now settled by the currency ladder alone, which is correct
# for a mod that refuses to sell claims at all.
#
# The order is also the register's own (integration contract 1.C lists
# tnt_ab_lumpy_vassal_r_effect, _title_r_effect, _claim_r_effect in that order;
# the third entry is now retired, not reordered).
#
#=======================================================================
# D.5  VETO MEMORY - WHAT IT REMEMBERS AND WHAT IT DOES NOT
#=======================================================================
# tnt_ab_added_title / tnt_ab_added_claim   what THIS button put on the table
# tnt_ab_veto_title  / tnt_ab_veto_claim    what the player then took off again
# tnt_ab_vassal_mark / tnt_ab_veto_vassal   the same pair for the fealty bool
#
# The rule the hint text states and this code implements: THE BUTTON WILL NOT
# RE-OFFER SOMETHING IT ADDED AND THE PLAYER REMOVED. It is deliberately not "the
# button will not offer something the player removed": a term the player put on the
# table himself and then thought better of is his own business, and the mod does
# not read a second meaning into it.
#
# The mark half of the fealty pair exists for exactly that distinction. Fealty is a
# bool, so there is no object to put in a list; without tnt_ab_vassal_mark the
# untick handler could not tell "the button proposed this and I refuse" from "I
# ticked this myself and changed my mind".
#
# THE MEMORY DIES WITH THE OFFER. All six live exactly as long as the negotiation:
# tnt_reset_offer_effect clears them, and that effect is reached by window open,
# window close, the footer's Clear all and the post-deal wipe. The exact lines are
# named in this build's report; they are in another agent's file (tnt_30_effects.txt).
#
# WHAT IT DOES NOT DO: it never removes a term. Nothing in this section deletes
# anything from the table, ever - not a term the player added, and not a term an
# earlier press of the button added. Integration contract R10's argument against
# the deficit branch dropping demands applies here word for word: silently deleting
# a term is as surprising as silently adding one, and the player already has the
# remove control the veto memory listens to.
#
#=======================================================================
# D.6  WHAT MAKES EACH RUNG LEGAL TO ADD AT ALL
#=======================================================================
# The button may only add a term the PLAYER COULD HAVE ADDED HIMSELF with one
# click, and it reaches that answer the cheap way:
#   titles / claims  - the candidate comes out of tnt_list_title_r /
#                      tnt_list_claim_r, which tnt_fill_title_r_effect /
#                      tnt_fill_claim_r_effect built from T3
#                      (tnt_can_cede_title_trigger) and T4
#                      (tnt_can_grant_claim_trigger). Membership of that list IS
#                      the legality answer; there is nothing left to re-ask.
#   fealty           - has no candidate list, so the rung asks T5's reporting-free
#                      form directly, once, and only after the fit gate has passed.
#                      tnt_can_vassalize_trigger is described at
#                      tnt_20_scripted_guis.txt:900 as the most expensive trigger
#                      in the mod, which is why it sits BEHIND the >= 252 test and
#                      not in front of it.
# Both title rungs additionally require var:tnt_advanced, because a term the
# window is not showing must not appear in the deal sheet, and both
# tnt_show_title_r_trigger (tnt_41_gates.txt:1376) and tnt_show_vassal_r_trigger (tnt_41_gates.txt:1703) do.
# The claim row is not advanced-gated (tnt_41_gates.txt:1425) and neither is its
# rung.
#
#=======================================================================
# D.7  THE ADD IS THE SAME MOVE THE PLAYER'S CLICK MAKES
#=======================================================================
# Claims go through tnt_multi_add_effect, which is what tnt_sel_claim_r_add calls.
# Titles do NOT: tnt_sel_title_r_add (tnt_22b_multiselect.txt:373) hand-writes the
# move instead, and this rung reproduces that hand-written form rather than the
# shared one so that a button-added title and a clicked title are byte-for-byte the
# same state transition. If those two ever diverge, they diverge together.
#
# REMOVING FROM THE LIST BEING ITERATED is the one mutation vanilla sanctions and
# the mod already relies on: GAME\common\story_cycles\
# story_cycle_infidelity_confrontation.txt:45-64, and tnt_31_lists.txt's
# tnt_gc_promises_effect copied from it. Nothing here ever ADDS to the list it is
# walking.
# `if` inside an every_in_list body, evaluated per element at execution time rather
# than pre-computed like a `limit` might be:
#   GAME\common\scripted_effects\00_faction_effects.txt:1754-1767
# which is why the take-once test lives in the BODY and not in the iterator's
# limit. With a cached limit a single pass could take every title in the list.
# `change_variable = { name = X  add = 1 }`:
#   GAME\common\scripted_effects\00_achievement_effects.txt:26-29.
########################################################################


#=======================================================================
# D1 - tnt_ab_snap_surplus_effect      root = the player, no parameters
#
# The snapshot of D.3. Written unconditionally: tnt_ab_surplus_value returns
# exactly 0 outside a call of the entry point (its `exists = var:tnt_ab_ceiling`
# guard fails), so a stray call cannot invent a budget.
#=======================================================================
tnt_ab_snap_surplus_effect = {
	set_variable = {
		name = tnt_ab_snap
		value = tnt_ab_surplus_value
	}
}


#=======================================================================
# D2 - tnt_ab_lumpy_r_effect           root = the player, no parameters
#
# ONE PASS = at most ONE lumpy term. The rungs share the snapshot, and the
# first one to take something zeroes it, so the ones below it become no-ops without
# needing to know that anything happened.
#
# V13, USER ITEM 1: THE LADDER IS TWO RUNGS NOW, NOT THREE. The parchment rung
# (D5, tnt_ab_lumpy_claim_r_effect) is retired with the granted claim - TOMBSTONE C
# in common\scripted_effects\tnt_32_apply.txt - so FEALTY and TITLE are the only
# rungs left, and the TITLE rung is now the fine-grained end of the ladder.
#
# The snapshot is removed again on the way out, so between passes the only state
# that survives is the table itself and the two added-lists.
#=======================================================================
tnt_ab_lumpy_r_effect = {
	# THE NUMERIC FLOOR, same rule as C3/C4 and for the same reason: the three rungs
	# read tnt_ab_lumpy_n arithmetically with change_variable, and reading an absent
	# variable is the D5 "Failed to fetch variable" class of defect. The only caller
	# today writes it before the branch, so this is belt to that braces - and it is
	# vanilla's own shape for exactly this pairing,
	# GAME\common\scripted_effects\00_achievement_effects.txt:21-29.
	if = {
		limit = { NOT = { exists = var:tnt_ab_lumpy_n } }
		set_variable = {
			name = tnt_ab_lumpy_n
			value = 0
		}
	}

	tnt_ab_snap_surplus_effect = yes

	tnt_ab_lumpy_vassal_r_effect = yes
	tnt_ab_lumpy_title_r_effect = yes
	# RETIRED V13, USER ITEM 1 - the parchment rung. Its body (D5) is commented out
	# below; this call goes with it, because a call to a commented-out effect is a
	# name the engine cannot resolve.
	#	tnt_ab_lumpy_claim_r_effect = yes

	remove_variable = tnt_ab_snap
}


#=======================================================================
# D3 - tnt_ab_lumpy_vassal_r_effect        THE CROWN RUNG
#
# 252 = the 250 hard ceiling of tnt_val_vassal_r_value's own `add` block plus the
# two-point rounding cushion of D.2. There is no cheaper reading: the value is
# 100 + 5 x his realm_size, and the button must be sure BEFORE it ticks the box,
# so it prices him at the ceiling.
#
# `NOT = { exists = var:tnt_vassal_p }` is not decoration. The two fealty
# directions are mutually exclusive and tnt_vassal_p_toggle enforces that by
# wiping the other one; a rung that ticked `_r` while the player had `_p` on the
# table would silently reverse who kneels to whom. The button never overrides a
# direction the player chose - it only fills an empty slot.
#=======================================================================
tnt_ab_lumpy_vassal_r_effect = {
	if = {
		limit = {
			exists = var:tnt_ab_snap
			var:tnt_ab_snap >= 252

			exists = var:tnt_partner
			exists = var:tnt_advanced

			# Neither direction of fealty is already on the table.
			NOT = { exists = var:tnt_vassal_r }
			NOT = { exists = var:tnt_vassal_p }
			NOT = { exists = var:tnt_indep_r }
			NOT = { exists = var:tnt_indep_p }

			# A realm leg and a title transfer have no coherent projection order.
			# Preflight rejects the mix, so Equalize must never manufacture it.
			NOT = { exists = var:tnt_title_p }
			NOT = { exists = var:tnt_title_r }
			trigger_if = {
				limit = { has_variable_list = tnt_sel_title_p }
				variable_list_size = { name = tnt_sel_title_p  value = 0 }
			}
			trigger_if = {
				limit = { has_variable_list = tnt_sel_title_r }
				variable_list_size = { name = tnt_sel_title_r  value = 0 }
			}

			# The player has already refused this once (D.5).
			NOT = { exists = var:tnt_ab_veto_vassal }

			# LAST, because it is the most expensive trigger in the mod. Direction
			# copied verbatim from tnt_vassal_r_toggle's own is_valid
			# (tnt_20_scripted_guis.txt:975-978): the PARTNER kneels, so the player
			# is the liege. Passing these the other way round silently inverts the
			# rank test inside T5.
			tnt_can_vassalize_trigger = {
				LIEGE = root
				VASSAL = var:tnt_partner
			}
		}

		set_variable = {
			name = tnt_vassal_r
			value = 1
		}
		# "The button put this here", so an untick is a veto and not a change of
		# mind. Read by the untick branch of tnt_vassal_r_toggle.
		set_variable = {
			name = tnt_ab_vassal_mark
			value = 1
		}

		change_variable = {
			name = tnt_ab_lumpy_n
			add = 1
		}
		set_variable = {
			name = tnt_ab_snap
			value = 0
		}
	}
}


#=======================================================================
# D4 - tnt_ab_lumpy_title_r_effect         THE LAND RUNG
#
# Bounds from D.2: 15/30/45/60/75 x 2.1, rounded up, plus the 2-point cushion.
#   barony 34   county 65   duchy 97   kingdom 128   empire 160
#
# THE OUTER `if` IS AN EARLY-OUT, not the fit test. It asks the cheapest question
# once - "is there a candidate list at all, and could even a barony fit?" - so a
# press on a small surplus never builds an iteration. The real per-candidate test
# is inside the body, because a `limit` on the iterator may be evaluated for every
# element before the body runs even once, and the take-once rule depends on the
# test seeing the zeroed snapshot written by the previous iteration.
#=======================================================================
tnt_ab_lumpy_title_r_effect = {
	if = {
		limit = {
			exists = var:tnt_ab_snap
			var:tnt_ab_snap >= 34

			exists = var:tnt_partner
			exists = var:tnt_advanced

			# Never append land to a package which already changes the realm graph.
			# This also stops pass two from following a pass-one fealty addition.
			NOT = { exists = var:tnt_vassal_p }
			NOT = { exists = var:tnt_vassal_r }
			NOT = { exists = var:tnt_indep_p }
			NOT = { exists = var:tnt_indep_r }

			has_variable_list = tnt_list_title_r
			variable_list_size = {
				name = tnt_list_title_r
				value > 0
			}
		}

		# The walk runs in the TITLE's scope; every write below belongs to the
		# player, so he is carried in by name. Temporary, and re-saved on nothing:
		# one save, outside the loop.
		save_temporary_scope_as = tnt_ab_owner

		every_in_list = {
			variable = tnt_list_title_r

			# tnt_picked is the scope name the shared add effects and the GUI's own
			# AddScope both use, so the rung hands them exactly what a click would.
			# Temporary, one per iteration, per 30-V2-DESIGN 3.5(e).
			save_temporary_scope_as = tnt_picked

			scope:tnt_ab_owner = {
				if = {
					limit = {
						# Nothing taken yet this pass, and a barony would fit.
						var:tnt_ab_snap >= 34

						# The player removed this one after the button offered it.
						trigger_if = {
							limit = { has_variable_list = tnt_ab_veto_title }
							NOT = {
								is_target_in_variable_list = {
									name = tnt_ab_veto_title
									target = scope:tnt_picked
								}
							}
						}

						# Already chosen. Cannot happen while the two-list invariant
						# holds, and it is one test to keep it holding.
						trigger_if = {
							limit = { has_variable_list = tnt_sel_title_r }
							NOT = {
								is_target_in_variable_list = {
									name = tnt_sel_title_r
									target = scope:tnt_picked
								}
							}
						}

						# THE FIT TEST. One rung of the tier ladder fires; the tiers
						# are read off the candidate, the budget off the player.
						trigger_if = {
							limit = { scope:tnt_picked = { tier = tier_barony } }
							var:tnt_ab_snap >= 34
						}
						trigger_else_if = {
							limit = { scope:tnt_picked = { tier = tier_county } }
							var:tnt_ab_snap >= 65
						}
						trigger_else_if = {
							limit = { scope:tnt_picked = { tier = tier_duchy } }
							var:tnt_ab_snap >= 97
						}
						trigger_else_if = {
							limit = { scope:tnt_picked = { tier = tier_kingdom } }
							var:tnt_ab_snap >= 128
						}
						trigger_else = {
							var:tnt_ab_snap >= 160
						}
					}

					# THE MOVE, hand-written to match tnt_sel_title_r_add exactly
					# (tnt_22b_multiselect.txt:331-371) - see D.7. Add first, then
					# shorten the candidate list, which is the list being walked.
					add_to_variable_list = {
						name = tnt_sel_title_r
						target = scope:tnt_picked
					}
					if = {
						limit = {
							has_variable_list = tnt_list_title_r
							is_target_in_variable_list = {
								name = tnt_list_title_r
								target = scope:tnt_picked
							}
						}
						remove_list_variable = {
							name = tnt_list_title_r
							target = scope:tnt_picked
						}
					}

					# The veto memory's first half (D.5).
					add_to_variable_list = {
						name = tnt_ab_added_title
						target = scope:tnt_picked
					}

					change_variable = {
						name = tnt_ab_lumpy_n
						add = 1
					}
					# Budget spent: ends this walk and skips the claim rung below.
					set_variable = {
						name = tnt_ab_snap
						value = 0
					}
				}
			}
		}
	}
}

#=======================================================================
# D6 - tnt_ab_note_veto_effect     { ADDED  VETO }     root = the player
#
# ONE object left the table. If the button is the one that put it there, the
# button is told never to offer it again.
#
# Called from tnt_sel_title_r_remove and tnt_sel_claim_r_remove
# (tnt_22b_multiselect.txt), where scope:tnt_picked is the row the player clicked -
# the same scope the remove itself consumed. It runs AFTER the remove and does not
# depend on it: the two lists are disjoint from the selection lists entirely.
#
# THE MOVE OUT OF `ADDED` IS WHAT MAKES IT IDEMPOTENT. A second click on a stale
# row finds nothing in ADDED and does nothing, so the veto list can never collect
# the same object twice.
#
# `is_target_in_variable_list` guarded by `has_variable_list` in the same block:
# GAME\common\achievements\ep2_achievements.txt:230-240, and the shipped pairing at
# tnt_31_lists.txt:301-313.
#=======================================================================
tnt_ab_note_veto_effect = {
	if = {
		limit = {
			exists = scope:tnt_picked
			has_variable_list = $ADDED$
			is_target_in_variable_list = {
				name = $ADDED$
				target = scope:tnt_picked
			}
		}
		remove_list_variable = {
			name = $ADDED$
			target = scope:tnt_picked
		}
		add_to_variable_list = {
			name = $VETO$
			target = scope:tnt_picked
		}
	}
}


#=======================================================================
# D7 - tnt_ab_veto_all_effect      { ADDED  VETO }     root = the player
#
# THE WHOLE COLUMN was cleared in one click, so every object the button had put in
# it is refused at once. Called from tnt_sel_title_r_clear and
# tnt_sel_claim_r_clear, which have no scope:tnt_picked to work from - that is the
# only reason this is not just a loop over D6.
#
# It walks ADDED and writes VETO - two different lists, so no mutation of the list
# under iteration at all - and clears ADDED once the walk is over, which is
# vanilla's own shape at GAME\common\scripted_effects\00_faction_effects.txt:1754-1768
# (iterate, act, clear_variable_list after the loop).
#
# The duplicate guard matters here in a way it does not in D6: a player who clears
# the column twice in a session, with a press in between, would otherwise put the
# same title in the veto list twice.
#=======================================================================
tnt_ab_veto_all_effect = {
	if = {
		limit = { has_variable_list = $ADDED$ }

		save_temporary_scope_as = tnt_ab_owner
