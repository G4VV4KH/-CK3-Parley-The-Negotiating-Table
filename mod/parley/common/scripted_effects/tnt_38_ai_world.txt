# E1 — tnt_ai_send_gold_effect      params: PAYER, RECEIVER, AMOUNT
#
# pay_short_term_gold in the PAYER's scope with target = the receiver. Atomic,
# correctly tooltipped in both directions, and it respects the short-term income
# budget the AI itself uses — which is why it is the ONLY gold-moving effect this
# mod is allowed to use. The two blacklisted alternatives (00-ARCHITECTURE §4.6)
# must never appear.
# Verbatim call site with a NAMED SCRIPT VALUE as the amount, from a working 1.19
# mod's on_accept:
#   MODS\2712590542\common\character_interactions\interactive_bribe_to_leave_war.txt:139-149
#       scope:actor = {
#           if = {
#               limit = { scope:gold = yes  gold > major_gold_value }
#               pay_short_term_gold = { target = scope:recipient  gold = major_gold_value }
#           }
#       }
# and vanilla's own at GAME\common\character_interactions\00_gift.txt:144-147.
#
# THE AFFORDABILITY GUARD IS NOT OPTIONAL AND IT IS NOT DECORATIVE.
# Without it a broke AI hands over nothing and still collects the truce, i.e. the
# recipient signs a package that was never delivered — the exact opposite of the
# "value-fair deals" the user asked for.
#
# *** V15: THE FIELD IS `gold`, NOT `short_term_gold`. THIS WAS THE SANDBOX'S
# *** LARGEST SINGLE DEFECT AND IT COST ~238 OF 583 LOST DRAWS IN ONE RUN. ***
# short_term_gold is a BUDGET CATEGORY, not a purse: the war chest is taken off
# the top and only the remainder is split 20/80 between LongTerm and ShortTerm.
#   BUDGET_CATEGORY = { 0.0 Reserved | 0.0 "War chest; has its own logic" |
#                       0.20 LongTerm | 0.80 ShortTerm }
#   GAME\common\defines\ai\00_ai.txt:100-105
#   MIN_WAR_CHEST = { 25 25 50 100 200 300 400 }   :139-147
#   MONTHS_OF_MAINTENANCE_IN_WAR_CHEST = 18        :154
#   PERCENTAGE_INTO_WAR_CHEST = 0.6                :161
# So for the county/duchy tier this pulse actually draws from, short_term_gold is
# very much smaller than gold. MEASURED 2026-08-17: 16 telemetry lines where the
# payer's DISPLAYED gold already exceeded the price and the gate still refused -
# WSTOP why=actor_broke at have/need 38/25, 36/25, 53/25, 34/25, 52/25, 51/25,
# 35/25, 153/25, 63/62, 243/224, 333/218, 232/216, and WSKIP arch=wed
# why=payer_broke at 329/300, 340/300, 327/300, 226/200. Nine of those need
# exactly 25 against 34-53 gold in hand.
#
# THE OLD CITATION WAS THE WRONG KIND OF ROW, and that is how the mistake was
# made. GAME\common\character_interactions\00_gift.txt:486
# (`short_term_gold >= gift_interaction_cutoff`) sits inside **ai_potential**
# (:483-492), between `ai_greed < medium_positive_ai_value` and
# `NOT = { has_trait = greedy }` - it is a WILLINGNESS row, "is the AI in the mood
# to be generous", not an affordability row. Vanilla's AFFORDABILITY rows use
# plain `gold`, in **is_valid**:
#   GAME\common\character_interactions\00_marriage_interactions.txt:783-786
#     is_valid = { scope:actor = { gold >= real_wedding_cost_actor_scope ... } }
#   (vanilla's own wedding-cost gate, directly on point for S-WED); also
#   GAME\common\character_interactions\00_prison_interactions.txt:1930, :1968,
#   :2800 (ransoms) and 00_courtier_and_guest_interactions.txt:36, :55.
# Census over GAME\common: plain `gold >=/>` 336 sites vs `short_term_gold >=/>`
# 82.
#
# AND pay_short_term_gold NEEDS NO SUCH GUARD AT ALL: vanilla's own
# pay_short_term_gold_reparations_effect passes arbitrary reparation sums with no
# short_term_gold row anywhere - GAME\common\scripted_effects\00_war_effects.txt
# :2326 (the pay call at :2334). The EFFECT below is left exactly as it is; only
# the TRIGGER field changed.
#
# THE TWO GUARDS MUST NAME THE IDENTICAL FIELD, AND THAT IS NOW A RULE RATHER THAN
# A COINCIDENCE. The callers also test affordability before choosing a price tier,
# so this is the second of two independent guards - but the `if` below has NO
# `else`, so if the two ever diverge the payment becomes a silent no-op while the
# caller has already logged WDONE and moved the goods. Concrete failure if only
# the caller rows had been changed: a buyer with gold = 1200 and
# short_term_gold = 300 against tnt_ai_artifact_gold_value = 1125 passes the
# caller's `gold >= 1125` and fails this `short_term_gold >= 1125` - WDONE is
# logged, no gold moves, and the artifact transfers on the next line
# (S-ARTIFACT's leg calls the log, then this, then the transfer). A free
# masterwork. Both rows are `gold` and both must stay `gold`.
###############################################################################
tnt_ai_send_gold_effect = {
	$PAYER$ = {
		if = {
			limit = { gold >= $AMOUNT$ }
			pay_short_term_gold = {
				target = $RECEIVER$
				gold = $AMOUNT$
			}
		}
	}
}

# E2 — tnt_ai_send_prestige_effect  params: GIVER, RECEIVER, AMOUNT
#
# THERE IS NO PRESTIGE TRANSFER EFFECT IN 1.19. 30-V2-DESIGN §1 row 2.4 is explicit:
# the only route is two independent calls, one negative on the giver and one positive
# on the receiver, and the blacklist names every plausible-looking alternative
# (transfer_prestige, pay_prestige, remove_prestige — none exists).
#
# Shape copied verbatim from the mod's own tnt_exec_prestige_effect
# (tnt_33_currency_apply.txt), with the variable read replaced by the parameter:
#       $GIVER$    = { add_prestige = { value = …  multiply = -1 } }
#       $RECEIVER$ = { add_prestige = …  }
# The block-with-multiply form is vanilla —
# GAME\common\character_interactions\00_invite_agent_to_scheme.txt:166-174.
#
# *** THE GUARD IS MANDATORY HERE FOR A DIFFERENT REASON THAN E1's. ***
# Prestige GOES NEGATIVE SILENTLY. There is no bankruptcy event, no warning and no
# engine refusal: an AI that pays 2000 prestige it does not have simply ends up at
# -1400 and starts failing every prestige-gated decision it owns for a decade.
# 30-V2-DESIGN §1 row 2.4 requires the affordability test to be an explicit gate
# ("must be gated … because prestige goes negative silently"), and this is that gate
# for the AI path. `prestige >= <named value>` mirrors vanilla's own currency gate
# `influence >= major_influence_value`
# (GAME\common\character_interactions\00_alliance.txt:1320).
# The same live currency rule applies to AI-to-AI transfers, with A as the
# actual giver and B as the actual receiver. Absolute handles are required
# because this helper enters the giver's scope before testing the rule.
#
# The receiver's leg is nested INSIDE the giver's `if`, so the two halves can never
# separate: either both run or neither does. A prestige gift that credits the
# receiver without debiting the giver is free money and it would be invisible.
#
# *** ZERO CALLERS AS OF THE V13 USER ITEM 1/2 WAVE. *** Written for the Phase-B
# interaction file tnt_11_ai_interactions.txt, which was never shipped and does
# not exist. Kept DEFINED, not deleted: it is a correct parameter machine, and
# the next path that needs to move prestige between two AI rulers should call it
# rather than write a third one. A reader of the Part A banner would otherwise
# assume six live shared legs where there are four (E1, E5, E19 and E9/E10).
###############################################################################
tnt_ai_send_prestige_effect = {
	$GIVER$ = {
		if = {
			limit = {
				tnt_trade_prestige_trigger = { A = $GIVER$ B = $RECEIVER$ }
				prestige >= $AMOUNT$
			}
			add_prestige = {
				value = $AMOUNT$
				multiply = -1
			}
			$RECEIVER$ = {
				add_prestige = $AMOUNT$
			}
		}
	}
}

# E5 — tnt_ai_grant_hook_effect    params: GIVER, RECEIVER
#
# The GIVER ends up OWING the RECEIVER one weak, ten-year, single-use favour.
#
# *** THE PARAMETERS LOOK SWAPPED. THEY ARE NOT. DO NOT "FIX" THIS. ***
# add_hook run in scope Y with target = X means "Y gains a hook OVER X" — proven at
# GAME\common\character_interactions\00_grant_titles_interaction.txt:1065-1077, where
# scope:actor (who granted the title, i.e. did the favour) gains the hook on
# scope:recipient. The deal term reads "owe the other party a favour they may call
# in", so the side that GIVES the term must end up hooked: the RECEIVER gains, the
# GIVER is bound. tnt_32_apply.txt:715-722 and tnt_36_hooks_contracts.txt carry the
# identical note for the identical reason; all three must stay consistent.

#           if = { limit = { can_add_hook = { target = $TARGET$  type = $TYPE$ } }
#                  add_hook = { target = $TARGET$  type = $TYPE$ } }
#       }

# the YEARS-taking sibling at :12-26 would override the type's own expiry.
#
# tnt_deal_favor_hook = { expiration_days = 3650 } — the mod's own tier-1 type,
# MOD\common\hook_types\tnt_90_hook_types.txt:116-118, itself a verbatim copy of

# E9 — tnt_ai_world_notify_effect   params: A, B, TT
#
# "Tell the player what happened when it matters. Do not spam."
#
# THE ANTI-SPAM RULE IS THE `limit`, NOT THE MESSAGE TYPE. A player is told about a
# treaty between two AIs only if he is ALLIED TO, AT WAR WITH, or A LAND-REALM
# NEIGHBOUR OF one of the two parties. Everybody else hears nothing, because for
# everybody else nothing has changed that they could act on. That predicate is
# copied straight from vanilla's own reasoning about AI-to-AI notifications,
# GAME\common\scripted_effects\00_war_effects.txt:1774-1782:
#       # As a pure notification thing, we only care about players. No need to waste
#       # CPU cycles for AI-only wars.
#
# `every_player` IS THE RIGHT ITERATOR AND IT IS CHEAP: 271 uses across
# GAME\common + GAME\events (measured in this session), and in single player it is
# ONE entry. The mod already uses it on the much hotter on_death
# (tnt_70_on_actions.txt:73). The three OR rows are two relation lookups and one
# neighbour test per player per concluded treaty, and a concluded treaty happens a
# handful of times a year (see tnt_72_ai_world.txt's budget).
# `character_is_land_realm_neighbor`: REAL,
#   GAME\common\character_interactions\00_character_interactions.txt:638,
#   GAME\common\character_interactions\05_bp2_interactions.txt:558.
#
# THE TWO `NOT = { this = … }` ROWS look redundant — the C-2 pulse only ever pairs
# two AI characters, so a player can never be $A$ or $B$. They are here because this
# effect is a general-purpose leg and the day somebody calls it from the Phase-B
# on_accept path (where the player CAN be a party) a self-addressed "two rulers you
# know have signed a treaty" message would be absurd.
#
# WHY send_interface_message AND NOT send_interface_toast: a toast is a transient
# corner pop for something the player just did; this is somebody else's news and
# belongs in the message feed, which is what `display = feed` types are for
# (GAME\common\messages\_messages.info:7-65). `event_generic_neutral` is a real
# vanilla type — GAME\common\messages\00_messages.txt:67 — used with
# send_interface_message at GAME\common\on_action\title_on_actions.txt:2979-2984,
# which is also the site that proves the four-key
# type/title/left_icon/right_icon + custom_tooltip shape.
# 10-CONTRACT §1 forbids this mod from creating common/messages/, and we do not
# need to.
#
# THE TWO PORTRAITS CARRY THE IDENTITY, THE TOOLTIP CARRIES THE TERMS. left_icon and
# right_icon render the two rulers, so the title and the tooltip can be generic
# prose and need no character reference — which matters, because a message is
# rendered later, from the feed, and whether a temporary saved scope is still
# addressable from its loc at that point is not something to bet a feature on.
# That is the same conclusion the mod already reached for its own toasts
# (tnt_32_apply.txt:919-921).
#
# THE EFFECT IS **NOT** NESTED INSIDE THE MESSAGE. Vanilla's mpo_tributary_check_pulse
# (GAME\common\on_action\dlc\mpo\mpo_on_actions_2.txt:543-573) nests the mutation
# inside send_interface_message so the two cannot diverge, and that is the better
# pattern when the mutation is unconditional. Ours is not: the apply legs are each
# individually guarded and one of them can legally decline to fire, so a nested form
# would sometimes announce a treaty that did not happen. Announcing afterwards with
# a custom_tooltip is what tnt_notify_accepted_effect already does, for the same
# reason (tnt_32_apply.txt:918-921).
###############################################################################
tnt_ai_world_notify_effect = {
	every_player = {
		limit = {
			is_ai = no
			NOT = { this = $A$ }
			NOT = { this = $B$ }
			OR = {
				is_allied_to = $A$
				is_allied_to = $B$
				is_at_war_with = $A$
				is_at_war_with = $B$
				character_is_land_realm_neighbor = $A$
				character_is_land_realm_neighbor = $B$
			}
		}
		send_interface_message = {
			type = event_generic_neutral
			title = tnt_ai_msg_treaty
			left_icon = $A$
			right_icon = $B$
			custom_tooltip = $TT$
		}
	}
}

# E10b — THE STRATEGIC SUBMISSION LANE
#
# The cash ultimatum proves that high-tier AI rulers can price and execute a
# threat, but it can only move gold. The user's 2026-08-28 ruling adds a separate
# territorial use: an independent king/emperor may force one overwhelmingly
# weaker independent neighbour to swear fealty while both remain at peace. This
# is not S-FEALTY: no gold is
# offered and friendship is not the consideration. It is also not added to the
# generic random archetype draw, because the measured draw was precisely what
# left Ghurid/Seljuk/Khwarazmid rulers idle despite legal targets.
#
# ONE bounded neighbouring iterator, one chance roll, one target. The private
# tnt_submission_target scope is never the generic scope:recipient. Only the
# revalidated success branch copies it, so a failed strategic attempt cannot
# leak a stale partner into E11 when the peaceful fallback runs afterwards.
###############################################################################
tnt_ai_world_submission_pulse_effect = {
	save_temporary_scope_as = actor

	# Cheap actor shape before the strategic chance/value work. At-peace counts,
	# dukes and non-independent kings simply fall through to the old generic lane.
	if = {
		limit = {
			is_ai = yes
			is_alive = yes
			is_landed = yes
			is_ruler = yes
			is_adult = yes
			is_independent_ruler = yes
			is_at_war = no
			highest_held_title_tier >= tier_kingdom
			vassal_limit_available > 0
			NOT = { has_variable = tnt_ai_world_cd }
			# AGOT SUSPENDED (CK3 1.20): Mega-War exclusion parked; awaiting the AGOT update.
			# NOT = { has_variable = agot_pwl_direct }
			max_military_strength > 0
		}
		tnt_log_wsubpulse_effect = yes

		if = {
			limit = {
				current_military_strength >= fifty_percent_of_max_military_strength
			}
			random = {
				chance = tnt_ai_world_chance_value
				tnt_log_wsubtry_effect = yes

				random_neighboring_and_across_water_top_liege_realm_owner = {
					limit = {
						# T49b's nested pair gates require absolute handles. Name the
						# iterator candidate before substitution so `this` cannot rebind
						# to the actor inside an $A$ scope and waste this year's attempt.
						save_temporary_scope_as = tnt_submission_candidate
						tnt_ai_coercive_fealty_pair_trigger = {
							A = scope:actor
							B = scope:tnt_submission_candidate
						}
					}
					save_temporary_scope_as = tnt_submission_target
				}

				if = {
					limit = { exists = scope:tnt_submission_target }
					# Candidate tests may leave guarded threat aliases behind. Re-anchor
					# them to the chosen pair before any telemetry or mutation.
					scope:actor = { save_temporary_scope_as = tnt_thr_me }

				}
				else = {
					tnt_log_wstop_submission_nocand_effect = yes
				}
			}
		}
		else = {
			tnt_log_wstop_submission_depleted_effect = yes
		}
	}
}

# E11 — tnt_ai_world_pulse_effect     NO PARAMETERS
#        *** root MUST be the proposing AI ruler. ***
#
# Called from exactly one place: tnt_ai_world_pulse's `effect` block in
# tnt_72_ai_world.txt, whose trigger has already established that root is an AI,

# ===========================================================================
# WHY THIS SAVES SCOPES CALLED `actor` AND `recipient`
# ===========================================================================
# Because the tnt_ai_*_value family in tnt_56_ai_values.txt reads exactly
# `scope:actor` and `scope:recipient` and nothing else — it has to, since those are
# the names the ENGINE supplies inside an interaction's ai_accept, which is the

#   GAME\common\on_action\title_on_actions.txt:2973-2975

# effect chain, so `save_temporary_scope_as` is correct and leaves nothing behind
# (contract m10 discipline, 30-V2-DESIGN §3.5(e)).
#
# *** THE D4 HAZARD, AND WHY IT CANNOT BITE HERE. *** Defect D4 was
#   "[jomini_eventscope.cpp:565]: Trying to add the temporary target 'tnt_p' which
#    has the same name as a permanent target"

# chain (30-V2-DESIGN §9 D4). `actor` and `recipient` are permanent targets inside a
# CHARACTER INTERACTION's chain. This chain is not one: it is
# code -> yearly_playable_pulse -> (ai_character_pulse) -> tnt_ai_world_pulse, with
# no interaction anywhere in it and no saved scopes supplied by the engine.

# an event that an interaction fired, or anything else that already has an `actor`
# scope. If that is ever wanted, the values must be re-parameterised instead.

# THE PARTNER PICK — ONE CANDIDATE, BOUNDED, AI ONLY
# ===========================================================================
# *** V15 CHANGED THE ITERATOR, AND IT IS THE SINGLE LARGEST FIX THIS FILE HAS
# *** EVER HAD. `random_neighboring_top_liege_realm_owner` returns the neighbouring
# realm's TOP LIEGE, while the pulse itself fires from any AI count-or-above. So it

# The actor pays one-time gold; the recipient owes him one weak, ten-year,

		}

			RECEIVER = scope:recipient
			AMOUNT = tnt_ai_gold_low_value
		}

			GIVER = scope:recipient
			RECEIVER = scope:actor
		}
		tnt_ai_world_notify_effect = {
			A = scope:actor
			B = scope:recipient
			TT = tnt_ai_msg_tt_hook
		}
		tnt_ai_world_cooldown_effect = {
			A = scope:actor
			B = scope:recipient
		}
	}
	else_if = {
		limit = {
			scope:actor = { gold >= tnt_ai_gold_high_value }
			tnt_ai_deal_hook_high_value > 0
		}

			A = scope:actor
			B = scope:recipient
			TT = tnt_ai_msg_tt_hook

tnt_ai_world_do_wed_effect = {
	# V18, USER ITEM 2 - all four picks carry T51, the ownership gate, exactly as
	# this archetype's entry trigger does. The entry and the picks must ask the
	# same question or the entry promises a pair the picks then refuse, which is
	# the defect A16 shipped for three rounds on the letter path. Both handles
	# are absolute saved scopes. Full argument at the entry trigger above.
	# --- PASS 1: fix THEIR side first, then ask the recipient's pool ---------
	scope:actor = {
		random_close_family_member = {
			limit = {
				is_alive = yes
				is_betrothed = no
				marriage_interaction_can_be_picked_trigger = yes
				tnt_may_offer_spouse_trigger = { SIDE = scope:actor }
			}
			save_temporary_scope_as = tnt_wed_a1
		}
	}
	if = {
		limit = { exists = scope:tnt_wed_a1 }
		scope:recipient = {
			random_close_family_member = {
				limit = {
					is_alive = yes
					is_betrothed = no
					marriage_interaction_can_be_picked_trigger = yes
					tnt_may_offer_spouse_trigger = { SIDE = scope:recipient }
					can_marry_character_trigger = { CHARACTER = scope:tnt_wed_a1 }
				}
				save_temporary_scope_as = tnt_wed_b1
			}
		}
	}

	# --- PASS 2: the same search from the other end, only if pass 1 failed ---
	if = {
		limit = { NOT = { exists = scope:tnt_wed_b1 } }
		scope:recipient = {
			random_close_family_member = {
				limit = {
					is_alive = yes
					is_betrothed = no
					marriage_interaction_can_be_picked_trigger = yes
					tnt_may_offer_spouse_trigger = { SIDE = scope:recipient }
				}
				save_temporary_scope_as = tnt_wed_b2
			}
		}
		if = {
			limit = { exists = scope:tnt_wed_b2 }
			scope:actor = {
				random_close_family_member = {
					limit = {
						is_alive = yes
						is_betrothed = no
						marriage_interaction_can_be_picked_trigger = yes
						tnt_may_offer_spouse_trigger = { SIDE = scope:actor }
						can_marry_character_trigger = { CHARACTER = scope:tnt_wed_b2 }
					}
					save_temporary_scope_as = tnt_wed_a2
				}
			}
		}
	}

	# --- name the winning pair, p first in the direction the pick tested -----
	# Pass 1 tested the recipient's kinsman against the actor's, so HE is p;
	# pass 2 tested the actor's kinsman against the recipient's, so he is.
	if = {
		limit = {
			exists = scope:tnt_wed_a1
			exists = scope:tnt_wed_b1
		}
		scope:tnt_wed_b1 = { save_temporary_scope_as = tnt_wed_p }
		scope:tnt_wed_a1 = { save_temporary_scope_as = tnt_wed_r }
	}
	else_if = {
		limit = {
			exists = scope:tnt_wed_a2
			exists = scope:tnt_wed_b2
		}
		scope:tnt_wed_a2 = { save_temporary_scope_as = tnt_wed_p }
		scope:tnt_wed_b2 = { save_temporary_scope_as = tnt_wed_r }
	}

	# --- ONE ATOMIC BRANCH: pair, re-validation, money and balance together --
	# The re-validation rows are inside the LIMIT and not after the payment on
	# purpose: a dowry that moves without a wedding is the one outcome this
	# archetype must never produce.
	if = {
		limit = {
			exists = scope:tnt_wed_p
			exists = scope:tnt_wed_r
			NOT = { scope:tnt_wed_p = { this = scope:tnt_wed_r } }
			scope:tnt_wed_p = {
				is_alive = yes
				can_marry_character_trigger = { CHARACTER = scope:tnt_wed_r }
			}
			scope:tnt_wed_r = { is_alive = yes }
			scope:actor = { gold >= tnt_ai_wed_gold_value }
			tnt_ai_deal_wed_value > 0
		}
		tnt_log_wdone_wed_effect = yes
		tnt_ai_send_gold_effect = {
			PAYER = scope:actor
			RECEIVER = scope:recipient
			AMOUNT = tnt_ai_wed_gold_value
		}
		scope:tnt_wed_p = {
			tnt_wed_plain_pair_effect = yes
		}
		tnt_ai_world_notify_effect = {
			A = scope:actor
			B = scope:recipient
			TT = tnt_ai_msg_tt_wed
		}
		tnt_ai_world_cooldown_effect = {
			A = scope:actor
			B = scope:recipient
		}
	}

	# THREE HONEST BUCKETS, the same partition E20 and E23 use.
	#   no_legal_pair  BOTH passes came up empty, or the two picks landed on one
	#                  and the same man. THIS IS THE ARCHETYPE'S RISK LINE and
	#                  the first number the next playtest must read: the entry
	#                  trigger only proved that each side HAS somebody
	#                  marriageable, never that those two may marry each other.
	#                  THE EXPENSIVE ROW IS DELIBERATELY NOT RE-ASKED HERE: a
	#                  pair can only exist at all if one of the two picks already
	#                  passed can_marry_character_trigger on it, and nothing can
	#                  change inside one effect chain - so re-walking vanilla's
	#                  consanguinity check on the SKIP path would buy nothing and
	#                  would be paid even with telemetry off. The cheap not-the-
	#                  same-man row IS re-asked, because that is the one way the
	#                  commit limit can refuse a pair the picks produced.
	#   payer_broke    a legal pair, and the actor cannot afford the dowry.
	#   unbalanced     affordable and legal, and the recipient's balance refused.
	else = {
		if = {
			limit = {
				NOT = {
					AND = {
						exists = scope:tnt_wed_p
						exists = scope:tnt_wed_r
						NOT = { scope:tnt_wed_p = { this = scope:tnt_wed_r } }
					}
				}
			}
			tnt_log_wskip_wed_nopair_effect = yes
		}
		else_if = {
			limit = { scope:actor = { gold < tnt_ai_wed_gold_value } }
			tnt_log_wskip_wed_broke_effect = yes
		}
		else = {
			tnt_log_wskip_wed_unbalanced_effect = yes
		}
	}
}
